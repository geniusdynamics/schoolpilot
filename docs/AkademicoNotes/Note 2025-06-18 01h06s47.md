Definitive Data Generation Plan for School ERP (v6 - Final)
Primary Objective: To create a "living" dataset that simulates multiple years of complex school operations. This data must validate every existing feature (tables, views, triggers, procedures) and actively probe for logical gaps and opportunities for schema enhancement.
Overarching Directives:
Financial Truth: All financial events must generate balanced, double-entry transactions in fin_general_ledger, with source_table and source_id correctly populated.
Audit Trail: All significant changes to master records (adm_students, inv_items, etc.) are assumed to trigger the creation of a record in log_audit. The data must facilitate testing this trail.
Workflow Integrity: Every entity with a workflow_state_id must follow a logical progression through states defined in the flow_ tables.
I. Core Setup & Foundational Data (Execute First)
Schema Enhancement Suggestion: Chart of Accounts Templating
Critique: A single list in fin_chart_of_accounts is good, but schools (Govt vs. Private) have different reporting needs.
Suggestion: Modify the table: ALTER TABLE fin_chart_of_accounts ADD COLUMN is_active BOOLEAN NOT NULL DEFAULT TRUE, ADD COLUMN template_type ENUM('Core', 'Government', 'Private', 'Custom') NOT NULL DEFAULT 'Custom';
Data Generation:
Populate a set of ~20 accounts with template_type = 'Core' (e.g., Bank, Cash, Fees Receivable). These are fundamental.
Populate ~15 accounts with template_type = 'Government' (e.g., 'TSC Salaries Expense', 'Government Grant Revenue').
Populate ~10 accounts with template_type = 'Private' (e.g., 'Marketing Expense', 'Bus Purchase Capital').
Set some non-essential accounts to is_active = FALSE. This tests that they don't appear in application dropdowns.
Mapping Old journals to fin_transaction_templates:
For each of the 14 journal records you provided, create a corresponding fin_transaction_templates entry, linking to the new fin_chart_of_accounts.
Example Test:
Old: 'Creditors Payments(Bank)', 'MAIN ACCOUNT Sundry Creditor', 'Bank'
New Template: name='Supplier Payment (Bank)', debit_account_id=(ID for 'Supplier Payables'), credit_account_id=(ID for 'Main Bank Account').
Vote Head Coverage:
For every one of the 53 vote_heads you provided initially, ensure there is a corresponding Revenue or Expense account in fin_chart_of_accounts. This is non-negotiable for testing financial reporting.
II. People, Roles & Multi-Step Workflows
Schema Enhancement Suggestion: Granular Requisition Workflow
Critique: The current requisition flow is monolithic. A Lab Tech's role is missing.
Suggestion: Create a new table: CREATE TABLE flow_request_history (id BIGINT AUTO_INCREMENT PRIMARY KEY, request_table VARCHAR(50), request_id BIGINT, workflow_state_id INT, acted_by_user_id BIGINT, acted_at TIMESTAMP, comments TEXT);. This table will log every step of an approval.
Multi-Step Requisition Test Case:
Create staff members: A Chemistry Teacher, a Lab Technician, a HOD-Science, and a Store Manager.
Step 1: The Teacher creates a requisition in inv_requisitions for 'Hydrochloric Acid'. Its initial workflow_state_id is 'Pending Lab Tech Review', and a log is added to flow_request_history.
Step 2: The Lab Technician logs in, views the requisition, and approves it. The workflow_state_id on the main record updates to 'Pending HOD Approval', and a new log is added to flow_request_history. The Lab Tech adds another item, 'Beakers', to the original request (testing modification during workflow).
Step 3: The HOD approves, moving the state to 'Pending Store Issue'.
Step 4: The Store Manager issues the items, which creates inv_stock_transactions, updates inv_stock_levels (via trigger), and moves the final state to 'Fulfilled'.
III. Academics: CBC vs. 8-4-4 Structures
Curriculum Structure & Subject Papers:
Context: Your system needs to support two curriculum models running in parallel. The data should make this distinction clear.
Class-Level Test Case:
For adm_classes linked to 'Primary School' (Grades 1-4), subject assignments in edm_class_subject_allocations are direct (e.g., to 'Mathematics'). Examinations will not have paper splits.
For adm_classes 'Form 1' and 'Form 2', assignments are also direct.
For adm_classes 'Form 3' and 'Form 4', edm_class_subject_allocations are still to the main subject, but when an edm_exam_session is created for them, the edm_exam_paper_settings must be populated with the individual papers (e.g., 'Chemistry P1', 'Chemistry P2', 'Chemistry P3').
This tests the system's flexibility in defining exam complexity based on the class level.
IV. Financial Deep Dive: The Toughest Scenarios
Revenue & Expense Correlation Test:
Objective: To test if the system can facilitate budgeting by linking revenue earned from a specific source to expenses paid for that same purpose.
Test Case:
In fin_fee_template_items, create an item: description='EWC Fee', amount=500, linked to a revenue account gl_account_id named 'EWC Revenue'. This will be on student invoices.
Create three expense accounts: 'Electricity Expense', 'Water Expense', 'Conservancy Expense'.
Generate fin_supplier_invoices: one from 'National Power Co.' (for electricity), and another from 'City Water Board' (for water).
Pay these supplier invoices. The GL will show debits to the respective expense accounts.
The Crucial Test: A financial report should be able to query the fin_general_ledger for a period and show: Total Credits to 'EWC Revenue' vs. Total Debits to ('Electricity Expense' + 'Water Expense' + 'Conservancy Expense'). This allows the bursar to see if the EWC fee is covering its related costs.
Complex Payment Application Logic:
Objective: To test both priority-based and weighted-average payment allocations.
Priority-Based Test (Secondary School):
Create a student in Form 3 with a remaining balance of 2,000 on their Term 1 invoice and a new, fully unpaid Term 2 invoice of 15,000.
Record a payment of 5,000 via fin_student_payments.
Verification: A procedure sp_fin_recordPaymentAndApply_Priority must be called. After execution, the Term 1 invoice's amount_paid must be 2,000 (now fully paid), and the Term 2 invoice's amount_paid must be 3,000. This proves the "oldest first" logic.
Weighted-Average Test (Primary School):
Create a Grade 2 student with a fresh invoice containing these items in fin_student_invoice_items: 'Lunch' (1000), 'Swimming' (500), 'Art Supplies' (300). Total: 1800.
Record a payment of 900 (50% of the total).
Verification: A procedure sp_fin_recordPaymentAndApply_Weighted must be called. After execution, check fin_invoice_payment_applications. The amount_applied must be: 500 for the Lunch item, 250 for Swimming, and 150 for Art Supplies. This ensures every votehead receives its proportional share of the partial payment.
Historical Votehead Balance Reporting:
Objective: To test vw_fin_fee_collection_summary's ability to pivot on different time scales.
Test Case:
Ensure you have invoices and payments spanning across the 'AY-2023 / FY-2022-2023' and 'AY-2024 / FY-2023-2024' periods.
Query 1 (Academic View): SELECT * FROM vw_fin_fee_collection_summary WHERE academic_year = 'AY-2023'.
Query 2 (Financial View): SELECT * FROM vw_fin_fee_collection_summary WHERE academic_year IN ('AY-2023', 'AY-2024') and the underlying sp.financial_year_id corresponds to 'FY-2023'.
The results should be different, proving the view can correctly aggregate data based on both academic and financial calendars, which is essential for government reporting (IPSAS) and internal management.
V. Ancillary Service Workflows: Meals, Transport, Pocket Money
Transport Workflow:
Create fin_transport_routes with different costs.
Assign students using fin_student_transport_assignments for the current term.
Billing Test: Create a procedure sp_fin_billTransportFees(p_school_period_id) that automatically finds all active transport assignments for the period and adds a new line item to that student's main invoice OR creates a separate invoice for transport. Generate data to test both approaches.
Meals & Nutrition Workflow (nutr_):
Create nutr_meal_plans: 'Boarder Full Plan', 'Day Scholar Lunch-Only', 'Canteen Pay-As-You-Go'.
Assign students to these plans in nutr_student_meal_plans.
Boarder Test: A boarder is automatically billed for their meal plan as part of the main fin_fee_template. No daily charge occurs.
Pay-As-You-Go Test: A day scholar student who is not on a lunch plan uses their Pocket Money wallet to buy lunch. This will trigger a pm_wallet_transactions Purchase and a record in nutr_meal_consumption_log with charge_amount filled. This tests the integration between the Nutrition and Pocket Money modules.
Pocket Money (pm_):
Create a pm_merchants record for the 'School Canteen'.
Full Cycle Test:
Deposit: Parent makes a deposit. A record is created in fin_student_payments with a special note. A corresponding pm_wallet_transactions record is created with type='Deposit'. A GL entry is made: Debit Bank, Credit 'Pocket Money Liability'.
Purchase: Student buys a snack. pm_wallet_transactions record created with type='Purchase'. Running balance is updated.
Student Transfer: One student transfers 50 to another. This creates two pm_wallet_transactions: one TransferOut for the sender and one TransferIn for the receiver.
Withdrawal: Student withdraws cash from the bursar. Creates a Withdrawal transaction, reducing their wallet balance. The GL entry is: Debit 'Pocket Money Liability', Credit 'Cash on Hand'.
