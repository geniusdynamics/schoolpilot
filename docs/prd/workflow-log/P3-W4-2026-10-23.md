## Findings worth carrying forward

1. **The acceptance fixtures are reproduced to the shilling.** The sibling household (three children,
   0 / 300 / 600 discount, 7,000 / 6,700 / 6,400 net) and a 27,500 bill split 11,000 / 5,000 / 11,500
   across two sponsors and the family, with the split re-summed as an invariant rather than trusted.

2. **Two design calls worth knowing.** A discount takes its basis of the line's *remaining* amount,
   so two rules can never discount the same shilling twice and a discount cannot exceed what it
   discounts — the cap is structural, not a check. And an opening balance posts through the ledger's
   opening-balance derivation rather than the invoice derivation, because a carried-forward balance
   is not revenue: the invoice path would credit a fee item's revenue account and overstate the
   period's income.

3. **Idempotency is a run identity, not a flag.** A digest of the period, the schedule versions in
   force, the resolved cohort and the run's one-off inputs. A wider cohort is therefore a *different*
   run that bills only the learners added — which is exactly what spec 05 §4.3 asks for.

4. **Proration is exact and stated.** 6,000.00 × 69/96 = 4,312.50; 5,500.00 × 69/96 = 3,953.125
   rounded half-up to 3,953.13. A mid-period schedule change re-prices nothing already billed: a
   posted invoice is immutable, so a later version applies only to what a later run adds.

5. **The `exportable` finding from last wave now has a second life**: the billing panel's own export
   was checked against the dead prop, and the hub's CSV is the working path.

## Known gaps carried out of this wave

- **`invoice_line` has no `fee_schedule_id`**, and both invoice schemas are strict with no
  `attributes` field, so the schedule version a bill was priced from cannot be pinned on the line.
  It lives in the preview, the line's description and the run's audit row. The additive column plus a
  migration is the fix, and it is now reported by two separate tasks.
- The canonical `user` row still does not exist — the cashier identity, the workflow actor and (in
  P2) report publishing and promotion commits all work around it. **Still the most repeated blocker.**
- No budget entity, so budgets are stored figures the caller supplies.
- No transport-route entity, so a transport subscription carries a text reference.
- The canonical `grading_scale` still cannot store a band's upper-bound convention.
- The 500-learner admission-number bug is still unfixed.
