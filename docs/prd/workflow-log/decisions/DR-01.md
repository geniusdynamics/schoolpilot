# DR-01 — Entity schema and runtime validation approach

**Date:** 2026-10-19 · **Status:** proposed (pending orchestrator approval) · **Task:** P1-A01

## Context

- P1 puts canonical entities (spec 02) behind repositories (06 §2.2); storage DDL is generated
  from entity schemas (06 §2.5). One definition must drive TS types, runtime validation,
  SQLite DDL/indexes, forms (P1-D02) and migration fixtures (P1-C0x).
- Today `collectionsDefinition` holds RxDB-flavoured JSON Schema (`type: 'ref'`/`'timestamp'`,
  `primaryKey`, `indexes`) that `SchemaConverter` turns into SQLite DDL; there is no entity
  runtime validation and no generated types.
- Constraints: offline PWA; 06 §8.2 requires a content-security policy (runtime `eval` would
  force `script-src 'unsafe-eval'`); initial JS budget 500 KiB gzip (06 §7); neither `zod` nor
  `ajv` is a declared dependency.
- Spike: `learner` + `enrolment` (enums, ISO dates, optional fields, seven foreign keys, two
  cross-field rules). Code, commands, prerequisites and raw results:
  [spikes/DR-01/](./spikes/DR-01/results.md) and `spikes/DR-01/results.json`.

## Options considered (with spike evidence)

### A. zod v4 as the single source

Author entities as `zod/v4` schemas; `z.infer` gives the TS type; `safeParse` validates;
`z.toJSONSchema(schema, { io: 'output' })` bridges to storage DDL.

- **Types:** exact enum unions, optionals, recursive `z.json()` for `attributes`, branded ids
  via `.brand<T>()`. `tsc` accepted the same valid literals as the generated option and rejected
  unknown enums, missing required fields, `Date` in date fields and widened enums (`typecheck.ts`).
- **Validation:** valid path 8.6–10.2 µs/object (98–117k ops/s); all-invalid single-defect path
  128.4–166.0 µs/object, **8.8–10.9× slower** than Ajv because issues carry messages; 50/50
  mixed batches 67.7–78.5 µs/object. Cross-field rules (`end_date >= start_date`, `exit_reason`
  when left/completed) run in `safeParse`.
- **Errors:** `issues[]` with `path`, `code`, expected values and human-readable messages; the
  four-defect learner produced four issues (Ajv also produced four).
- **DDL:** `z.toJSONSchema` through the shared adapter produced **identical `CREATE TABLE`
  statements** to the authored JSON Schema path for both entities. Index arrays come from the
  same sidecar in both paths; composite unique indexes are sidecar-generated. SQLite typing is
  source-independent (`integer -> INTEGER`, `number -> REAL`, `boolean -> INTEGER`, strings/
  dates/enums/arrays/objects -> TEXT). Identical output does not validate the converter.
- **Build:** no generated TS, no codegen step. Schema construction for both entities 6.7 ms.
- **Bundle:** 46.7 KiB gzip (classic v4) for the entity plus parse; no `new Function`, so no CSP
  exception is needed.
- **Costs:** adds a direct runtime dependency. Emitted JSON Schema is 2.1–2.2× the hand-authored
  bytes because of explicit date/uuid patterns; refinements are absent from it. `.brand<T>()`
  produces `string & $brand<T>`; if adopted, `Id<T extends string> = string & core.$brand<T>`,
  not `string & { __entity: T }` (a probe showed both directions fail). `.transform()` and
  `z.custom<Id<T>>()` keep the app brand but `z.toJSONSchema` refuses them. Zod v3 needs
  `zod-to-json-schema`; v4 ships `z.toJSONSchema()`.

### B. JSON Schema + codegen

Author draft-07 JSON Schema; validate with Ajv; generate TS interfaces; derive DDL from the same
document.

- **Types:** a 54-line stand-in generator produced correct interfaces (enums, optionals, arrays,
  `$ref`). `tsc` accepted them and the same `@ts-expect-error` cases passed. Branded ids need a
  custom `x-brand` extension and generator support; `attributes` degrades to
  `Record<string, unknown>` unless the recursive JSON value is modelled explicitly.
- **Validation:** valid path 11.8–17.2 µs/object; all-invalid single-defect path 14.6–15.2
  µs/object; mixed batches 11.8–15.8 µs/object. Ajv does not ship `date`/`date-time`/`uuid`
  formats; the spike added ~25 lines of validators (or add `ajv-formats`). Date ordering is not
  expressible in draft-07 without the non-standard `$data` option: Ajv accepted
  `end_date < start_date`, Zod rejected it.
- **Errors:** structured (`instancePath`, `keyword`, `params`) but generic ("must be equal to one
  of the allowed values"); forms need a message-mapping layer.
- **DDL:** identical to option A through the shared adapter. The same converter defects remain:
  root `required` is ignored (all non-PK columns nullable) and composite unique/FK constraints
  need sidecar metadata.
- **Build:** generator + generated file + drift check. `json-schema-to-typescript` is not
  installed; the stand-in covers only the spike's constructs. Non-comment source cost: 135
  schema + 54 generator + 40 generated = 229 versus 112 for Zod; the generated file is 46 lines
  total, and the 84-line shared adapter is extra for both.
- **Startup:** Ajv compiled both validators in 55.1 ms (linear; ~2.8 s extrapolated for 100
  entities). Runtime compilation contains `new Function`, which would force
  `script-src 'unsafe-eval'` in the required CSP; standalone precompilation removes this but
  adds `ajv-standalone` and generated files.
- **Bundle:** 35.7 KiB gzip, 11.0 KiB smaller than Zod.

## Decision

Adopt **option A: zod v4 (`zod/v4`) as the single source of truth for core entity schemas**, with
`z.toJSONSchema()` as the explicit bridge to the existing DDL pipeline.

- Entities live in `src/domain/schema/*.ts`. `defineEntity({ schema, table, primaryKey, indexes,
  unique, refs, encrypted })` (proposed by P1-A03 in `src/domain/schema/defineEntity.ts`) returns
  `{ schema, storage }`; each entity exports the Zod schema, `z.infer` types and that sidecar.
  Core schemas use `z.strictObject`, so unknown top-level keys are rejected.
- P1-A04 keeps `createDatabaseSchema`/`SchemaConverter` as the DDL backend; the zod adapter calls
  them with `z.toJSONSchema(schema, { io: 'output' })` plus the sidecar. Only the legacy
  `collectionsDefinition` registry and RxDB-flavoured per-module schema definitions are retired
  after P1-E06; the DDL backend itself is not deleted.
- JSON Schema remains the format for pack-contributed `attributes` (02 §1.6) and exported
  contracts. Core entities are Zod; packs are JSON Schema. That is a split by ownership, not two
  sources for one entity.
- No direct `ajv`, `json-schema-to-typescript` or `ajv-standalone` dependency.

Rationale: type fidelity without a codegen step, field-level errors for P1-D02, intra-row
refinements, and CSP safety. Most 02 §12 invariants span entities and stay in repositories. The
DDL path is a wash; the 11.0 KiB gzip and the 8.8–10.9× all-invalid slowdown are acceptable.

## Consequences

- **P1-A02 (ids):** `Id<T>` must match Zod's brand: define
  `Id<T extends string> = string & core.$brand<T>` (type-only import from `zod/v4`) or brand at
  repository boundaries. Resolve the probe's two-way `TS2322` before P1-A03 uses ids.
- **P1-A03 (schemas):** the amended card has `deps_install: true` and owns `package.json` and
  `pnpm-lock.yaml`. Add **`zod@3.25.76`** exactly as a production dependency, imported as
  `zod/v4`; do not add `ajv` or a codegen package. Use `z.strictObject`, ISO date/datetime/uuid
  helpers, `z.enum`, `.optional()` and `.refine()` for intra-row rules. Do not use
  `.transform()`/`z.custom()` on persisted fields and do not commit generated TS types.
- **P1-A04 (DDL):** the amended card owns `src/services/database/SchemaConverter.ts`,
  `src/utils/databaseAgnosticSchema.ts` and `src/data/adapters/sqlite/*`. Read
  `z.toJSONSchema(...)` plus the sidecar; fix the root `required` bug so non-null columns get
  `NOT NULL`; add composite unique indexes and FK constraints. The DDL comparison covers
  `CREATE TABLE`; index arrays are sidecar-derived.
- **P1-B02 (repositories):** call `schema.safeParse` on create/update input, map `issues[].path`
  to field errors, and keep referential integrity and permission checks in the repository (Zod
  cannot check FKs). Use `z.input` for form payloads and `z.output` after defaults if defaults
  are introduced.
- **P1-D02 (forms):** bind to the same Zod schema and render `issues` beside fields. 06 §2.2
  requires inputs to be validated with the entity schema; sharing that schema with forms avoids
  form/repository drift.
- **P1-E06 and the legacy registry:** the amended card owns
  `src/services/database/collections.ts` and depends on P1-E01–E05. It removes the legacy
  `collectionsDefinition` registry and RxDB-flavoured per-module schemas.
  `createDatabaseSchema`/`SchemaConverter` stay as the DDL backend. New canonical tables are
  additive; P1-C0x migrations copy old collections into them.
- **Known limits:** refinements are not exported to JSON Schema, so DDL/pack export sees shape
  only. All-invalid validation is 8.8–10.9× slower than Ajv; within-run IQR spread was 15–53%
  (reviewer probe ~10%) and across-run medians moved up to ~1.8×. Classic Zod bundle is 46.7 KiB
  gzip; `zod/mini` is an option under budget pressure but was not spiked.
- **Follow-ups:** measure Zod on a mid-range Android device; add a CI check that
  `z.toJSONSchema` succeeds for every entity; decide on Ajv for pack schemas in P2.
