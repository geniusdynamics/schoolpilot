# DR-04: live query cache and the useQuery / useMutation / useLookup API

**Date:** 2026-10-19
**Status:** accepted
**Decided by:** implementer P1-B01, for P1-A03, P1-B02, P1-B05 and P1-D01
**Supersedes:** nothing. Realises spec 06 section 2.3.

## Context

P1 replaces the global `AppDataContext` snapshot and the per-page
`useDatabaseCollection` hook with repositories and a shared query layer
(spec 06 sections 2.1-2.3). P1-B02 will expose:

```ts
watch(q?: Query<E>): Observable<E[]>   // live query from the storage adapter
```

P1-B05 must then give pages `useQuery`, `useMutation` and `useLookup`, such that
any write refreshes every dependent view. P1-D01 consumes `useLookup` for its
picker, archived display and empty-state CTA. The layer must fit this app:

- Browser first. The source of truth is SQLite-WASM on OPFS, or a LAN/cloud
  replica. There is no request/response server in the normal path; `list()` is
  a local read, usually single-digit milliseconds.
- Writes already emit `CollectionChangeEvent { type, doc, oldDoc?, id }` from
  the provider (`src/services/database/interfaces.ts:107`), and every provider
  implements `subscribeToChanges()`. `AppDataContext` consumes these to refresh
  shared lookups (`LIVE_REFRESH_DEBOUNCE_MS = 30`).
- Direct dependencies are React 19 and RxJS 7. There is no TanStack Query, SWR
  or other server-state cache in `package.json` or the lockfile.
- Offline is the default. A cache persisted to disk would be a second source of
  truth next to SQLite, with its own schema and staleness.
- The initial-JS budget is 500 KB gzip; the PWA precache already overflows its
  3 MB budget by 3x (spec 06 section 7), so every dependency is scrutinised.

## Options

### A. TanStack Query v5 plus a persistence/subscription bridge

Evidence (package-only figures, Bundlephobia 2026-10-19):
`@tanstack/react-query@5.90.2` is 13.47 kB min+gzip and `@tanstack/query-core`
is a separate 11.67 kB min+gzip (about 25.1 kB together). Neither is installed,
so choosing this requires a dependency task and a lockfile change, which
P1-B01 and P1-B05 are not.

Strengths: mature request dedupe, retries, `onMutate`/rollback, devtools,
Suspense and a well-known mental model.

Why it does not fit here:

1. It caches asynchronous fetches. Our updates arrive as an RxJS stream from
   `Repository.watch`; TanStack has no native watch. The bridge is a second
   cache (watch -> `setQueryData`, invalidation -> another `list()`), exactly
   the dual-path bug P1 is removing (stale comboboxes, SO-26).
2. Persisting its cache is the wrong default. SQLite is already the offline
   store; restoring a serialised cache after a migration can resurrect rows the
   migration rewrote. We would disable persistence, losing the main benefit.
3. Retry/backoff is server-shaped. Repositories deliberately do not retry
   validation or auth failures; a cache-level policy would need overriding.
4. It adds a provider and a per-test `QueryClient`, against 2,481 local Windows
   typecheck errors (CI baseline 2,500); cost arrives before value, since
   P1-B05's dependency is P1-B02, not a new package.

### B. Bespoke live cache on React `useSyncExternalStore` + RxJS

A module-scoped `QueryCache` keyed by the full canonical key
(`entity:stableStringify(query)`). Entries own one read and, in `watch` mode,
one `repo.watch(query)` subscription. Modes make precedence explicit:

- `watch`: stream owns its entity; events only for `deps`.
- `invalidate`: refetch on matching events, detail-id precise.
- `manual`: data only on `refetch()` (legacy no-subscribe).

Events during an in-flight read set a revalidation flag, so the read re-runs
after it settles instead of dropping the update; many events in one tick
coalesce. `useLookup` stores its derived map in the entry and exposes explicit
state plus archived resolution. `useMutation` applies stackable layers; after
`mutationFn` resolves it assigns a fresh monotonic commit sequence, and only
reads or watch emissions at or after that sequence count as observation. Watch
payloads that arrive while a layer is pending commit are queued and applied
after commit, so a payload that already contains the write is not layered on
top of it. A successful post-commit read or emission drops every observed layer
before publishing. B02 contract: a write emits `ChangeEvent` synchronously
before its promise resolves; watch payloads are delivered after the DB commit
and write resolve, and a reordering transport must tag them with a commit
sequence. `whenSettled` still tolerates one macrotask for a deferred event.

### C. Zustand store (already a dependency)

A single store holding a dynamic key map makes every selector walk the map, and
per-key subscriptions are awkward. The primitive is exactly
`useSyncExternalStore`; Zustand adds indirection without removing code.

## Decision

Adopt **Option B**: a bespoke live query cache on `useSyncExternalStore` and the
repository's RxJS `watch`, with no new dependency.

API: `useQuery(key, fetcher, options)` for arbitrary reads;
`useEntityQuery(repo, query)` as the repository sugar (`data: Page<E>`, watch
emits `E[]` and replaces `data.items`); `useMutation({ mutationFn, optimistic,
onSuccess, onError })` with `mutate`/`mutateAsync`; `useLookup(entity, options)`
returning `byId`, `label`, `resolve`, `options`, `status`, `error`, `isFetching`.
`mutateAsync` resolves `{ result, settlement: { observed, error } }`; when no
read or watch emission reaches the layer's commit sequence, the optimistic layer
is retained until one does, and `settlement.error` reports the failed refresh.

Two deliberate spec-06 deviations: `useQuery(entity, query)` becomes
`useQuery(key, fetcher)` plus `useEntityQuery`; `useLookup` exposes `Map<Id, E>`
with `label()` rather than `Map<Id, Label>` (pickers need rows; labels stay
computed).

Rationale: the database is local and already emits typed change events, so a
small cache that subscribes to those events is simpler and more correct than a
server-state library bridged into the same events.

## Consequences

Positive:

- Zero bundle and lockfile change; P1-B05 can start when P1-B02 lands.
- One invalidation path: adapter event -> cache -> every dependent view. Legacy
  writes emit the same provider events, so both UI layers stay consistent.
- No persisted query state to invalidate across schema migrations.
- `useLookup` builds one map per key, resolves archived rows, and gives P1-D01
  its loading/empty/error states without a second read.
- Hook tests need no provider or network layer; a fake repository is enough.

Negative and mitigations:

- We own dedupe, GC, ordering and rollback; README rules plus P1-B05 tests.
- Page metadata is advisory for live lists: watch emits rows, not totals.
- No Suspense in P1; loading/empty/error states are explicit.
- No devtools panel; dev builds expose `window.__queryCache`.
- Optimistic settlement is subtle. Policy: retain-until-observed against a fresh
  commit sequence, not the layer-apply epoch. Watch payloads are queued while a
  layer is pending commit and applied afterwards; tagged stale payloads are
  rejected. A failed or late refresh keeps the layer visible and reports
  `settlement.error`; the next successful post-commit observation drops all
  observed layers before publishing. A later failed refresh does not erase an
  earlier observation, and increments are not applied twice.
- Residual edge: an untagged watch payload from a reordering transport cannot be
  distinguished from a current one. B02 must defer delivery until after the
  write promise resolves; transports that can reorder must tag every payload
  with a commit sequence. This is enforced by contract, not inferable.
- Watch errors keep the last good data and set `status: 'error'`; B05 resubscribes
  with bounded backoff before falling back to `invalidate`.
- A fire-and-forget event bus is required; awaiting each `notify()` defeats
  coalescing (the spike demonstrates both behaviours).
- `gcTime` (60 s default) is specified but not modelled by the spike; P1-B05
  owns the timer and tests stale-on-resubscribe.

Revisit if: a remote API makes dedupe/retries/pagination dominant; the cache
exceeds roughly 400 lines or grows a second invalidation mechanism.

## Spike evidence

`docs/prd/workflow-log/decisions/spikes/DR-04/` runs with `node --test` and
passes 30/30 cases (24 cache, 6 lookup):

- canonical keys include the entity (`learner:{}` != `class_group:{}`), ignore
  key order/undefined values, store Dates as ISO strings, reject
  Map/Set/RegExp/class instances and snapshot/freeze the query;
- one read for N subscribers; five events in one tick coalesce to one refresh;
- a dependent entry under another entity (`enrollment`, `deps: ['learner']`)
  refreshes on a learner event and not on an unrelated entity event;
- detail queries ignore other ids; an event during a gated in-flight read
  triggers one revalidation after it settles (calls 1 -> 2, data fresh);
- precedence: watch owns own-entity writes, deps refetch, invalidate refetches,
  manual ignores events until `refetch()`;
- `useEntityQuery` shape: `list` returns `Page`, watch replaces `items`, totals
  stay advisory until refetch;
- optimistic layers stack and roll back independently; early drop flickers;
  failed refresh retains the layer and reports `settlement.error`, then a later
  success drops it; a read that starts before commit (even after the layer is
  applied) does not count, including a pre-commit read followed by a 5 ms event;
  a post-commit read drops all observed layers before publishing, so a
  non-idempotent increment runs once; an earlier success survives a later failed
  refresh; a synchronous watch payload during a write is queued and does not
  double-apply; tagged stale watch payloads are rejected both while queued and
  after commit, while a post-commit emission settles; out-of-order commits get
  distinct sequences and do not settle each other; rejected writes roll back and
  rethrow; disposal/missing-entry settles are safe no-ops;
- lookup loading/empty/error states, archived resolve/label, `includeArchived`
  filtering, `idField`, `Page.items` unwrap and refresh after a write.

Not proven: React hook wiring (`useSyncExternalStore` snapshots), real
RxJS/SQLite timing, `gcTime` timers, watch error/resubscribe and the production
scheduler. P1-B05 owns those, using the same rules.

## Follow-ups

- P1-B02: writes emit `ChangeEvent` synchronously before their promise resolves;
  `watch` emits the current page on subscribe, then after every commit and after
  the write promise resolves. A transport that can reorder tags payloads with a
  commit sequence; the cache rejects older tagged payloads.
- P1-A03: own the `EntityName` union and per-entity `labelOf` registry.
- P1-B05: the four hooks and cache modes, `whenSettled` observation with
  retain-until-observed, `gcTime`, `suspend`/`resume`, watch error/resubscribe,
  unwrap `Page.items` for lookups, hook tests (vitest).
- P1-D01: `useLookup` status/options/`resolve` for empty state and archive.
- P1-E06: delete `useDatabaseCollection` after the last module migrates.
