# DR-05 — PDF rendering approach and the print CSS baseline

**Date:** 2026-10-21 · **Status:** proposed (pending orchestrator approval) · **Task:** P2-D01
**Decides for:** P2-D02 (report template engine), and the PDF path of P2-D03 (publishing and distribution)
**Supersedes:** nothing. Realises spec 03 §8.1–§8.2 and spec 07 §6.

## Context

P2-D02 must render the pack-defined report template (spec 03 §8.1: 15 block types, A4/A5, portrait/landscape,
locale labels, QR verification) as a printable document. P2-D03 must then distribute it: print queue, PDF download,
guardian portal, SMS link (spec 03 §8.2).

Constraints that decide the shape:

- **Offline is the default.** Topology A is a single device with SQLite-WASM in a worker and no server (06 §3.1);
  topology B is a Node "LAN hub"; topology C is hosted Postgres. Anything that requires a server fails topology A.
- **No PDF library is installed.** `jspdf`, `pdf-lib`, `@react-pdf/renderer` and `qrcode` all fail `require.resolve`;
  `package.json` has no document or barcode package. There is no Electron dependency.
- **The budget is 500 KB gzip initial JS** (06 §7). The PWA precache already overflows its 3 MB budget by 3×.
- **The browser already prints.** The existing report pages (`ReportCardsPage`, `StudentMasterlistPage`,
  statements, receipts, certificates) print with `window.print()` and a `@media print` block; P0-F05 measured a
  40-card print-to-PDF at 970 ms.
- **`page.pdf()` exists only in Node.** Chromium's print pipeline can write PDF bytes headlessly (Playwright or
  Puppeteer) but a web page cannot: `window.print()` opens the dialog and the user saves.
- **`puppeteer@^24.16.2` is a production dependency that nothing imports** (`grep src` = 0 hits), and spec 06 §7
  already lists it for removal from the client bundle.
- **The card cites spec 03 §8.4, which does not exist.** Spec 03 has §8.1 (template blocks) and §8.2 (behaviour);
  the QR requirement is the `verification` block in §8.1 and the signed distribution links in §8.2. Spec 07 §6 adds
  print preview, page breaks and batch printing. This record treats those as the requirements.

Spike: one HTML document rendering the 11-block primary-term card for 30 learners and a 40-row fee statement over two
pages, measured through Chromium 140 (Playwright) with pypdf, pypdfium2 and zxing-cpp. Commands, raw figures and
rendered page images: [`spikes/DR-05/`](./spikes/DR-05/results.md).

## Options considered (with spike evidence)

### A. Browser print pipeline driven by print CSS

The pack template renders to HTML with one stylesheet that owns page geometry, pagination and branding; the browser's
own print pipeline produces the PDF (dialog → Save as PDF, or the printer).

- **Cost:** 0 bytes of JS. The spike's document stylesheet (structure + print baseline) is **2,233 B gzip** (the
  `@media print` block alone 316 B). The QR encoder adds **2,311 B gzip**.
- **Output:** 30 cards → **30 A4 pages** at 209.9 × 297.0 mm in **1,091–1,156 ms** warm (36 ms/page) on a 2017
  ultrabook; first call 2,945 ms (pipeline start-up, once per job). A single card: 128–134 ms warm.
- **Text:** selectable and searchable — pypdf extracts 1,923 characters from a card page, including every mark, and all
  40 statement rows. Fonts are embedded; pages contain **no image XObjects** (logo and QR are vector).
- **Layout:** the browser paginates. Measured working: `thead` repeats on page 2 of the statement; rows never split;
  `@page` margin boxes give correct **"Page 1 of 2" → "Page 2 of 2"** numbering; signature/totals blocks stay whole.
- **Fidelity risks, measured:** variable fonts become Type3 (see §Fonts); `position: fixed` furniture overprints
  content; `tfoot` totals repeat on every page; `break-inside: avoid` on a table-holding block leaves a blank page;
  A5 cannot fit the full card; RTL needs `dir="ltr"` isolation for dates and URLs.
- **Limits:** the print dialog is user-controlled (scale, margins, "Background graphics"), so a user can break
  "one card = one sheet"; a web page cannot produce PDF bytes silently.

### B. A client-side PDF library

Three candidates, none installed. Bundle figures from Bundlephobia (2026-10-21), all MIT:

| Library | Minified | Gzip | Layout model | Bidi/shaping | Pagination |
| --- | ---: | ---: | --- | --- | --- |
| `jspdf@4.2.1` | 403,814 B | 129,768 B | manual text/table (or `html2canvas` → bitmap) | none | manual |
| `pdf-lib@1.17.1` | 429,058 B | 177,487 B | drawing primitives only | none | manual |
| `@react-pdf/renderer@4.9.0` | 1,200,522 B | 442,267 B | its own Yoga tree + components | no shaping | its own |

- **Cost:** 127–432 KiB gzip, i.e. **26–88% of the entire initial-JS budget**, before the template is written twice.
- **The template must be re-implemented** in a second dialect: the pack's blocks are HTML/CSS concepts (tables,
  wrapping comments, page rules). `jspdf`'s HTML path rasterises via `html2canvas` → no selectable text, huge files.
  `pdf-lib` has no line breaking, no tables, no `@page`. `@react-pdf` has layout but not CSS, and Arabic shaping must
  be supplied by the caller (no bidi, no joining).
- **What it buys:** programmatic bytes without a server. The statement (2 pages) is feasible; the 30-card batch with
  15 block types and four page geometries is a second engine with its own bugs and no visual regression baseline.
- **Licence/maintenance:** all three are permissively licensed, but the repo would own a parallel renderer and keep it
  in sync with the HTML one.

### C. Server or Electron headless print

The same HTML is loaded by headless Chromium and printed with `page.pdf()` on the LAN hub or cloud worker.

- **Measured distribution cost:** the installed Playwright headless shell is **290.9 MB** (full Chromium 457.6 MB);
  `puppeteer`'s browser cache is 1.2 GB across three versions. `puppeteer` itself is declared but unused in `src/`.
- **Coverage:** topology B/C only. Topology A has no server, and printing must work offline; a server-only path fails
  the primary deployment.
- **Fonts:** the client has Tahoma/Segoe UI for Arabic (measured: embedded subsets); a Linux container does not, so
  Arabic output would change or become tofu unless fonts are installed.
- **What it buys:** stored PDFs for a portal, deterministic batch output, no dialog. It is the right *second*
  executor for P2-D03, not the renderer.

### D. Mechanisms rejected inside option A

- **`visibility: hidden` + absolutely positioned cards** (the current `ReportCardsPage` pattern): the hidden app shell
  still paginates. Reproduced: 3 cards on a 9,000 px shell → **9 pages, 6 blank**; a card 18 px taller than the
  content box → **60 pages for 30 cards**.
- **`position: fixed` running footer:** overprints the last two ledger rows, and `counter(page)` inside content prints
  **"Page 0 of 0"** (page counters only exist in `@page` margin boxes).
- **`<tfoot>` for a final total:** repeats on every page (measured on both statement pages).
- **A PDF library in a worker** (06 §7's "PDF generation in a worker"): with option A there is no JavaScript PDF
  encoder to move; layout and serialisation happen in the browser's print pipeline. The line is satisfied in spirit,
  and this record states the deviation. Heavy per-learner image work (photo downscaling) still belongs in a worker.

## Decision

**Adopt option A: HTML + print CSS rendered by the browser's own print pipeline.** The document is the source of truth;
PDF is an output of that document, produced by the browser dialog on device and — from P2-D03, where a server exists —
by headless Chromium printing the same URL. No PDF library enters the client. The QR encoder is in-repo.

Specifically:

1. **P2-D02 renders, it does not encode PDFs.** It ships `<ReportDocument>` (blocks + page frame + print CSS), a
   print entry point, and the QR. Acceptance "all blocks render; A4/A5" is verified through the print route with
   Playwright `page.pdf()` and visual snapshots.
2. **P2-D03 owns stored PDFs.** When the deployment has a hub/cloud, a job prints the same document URL with headless
   Chromium and stores the result. This is an executor, not a second renderer: same HTML, same CSS, same QR. It is
   gated on topology B/C; topology A distributes by "Save as PDF" from the dialog.
3. **No new runtime dependency.** Rejected: `jspdf`, `pdf-lib`, `@react-pdf/renderer`, `qrcode`, `html2canvas`,
   Electron. The print assets are a stylesheet, three static font files and one ~240-line QR module.
4. **Static print font cuts.** The app imports the *variable* Inter (`@fontsource-variable/inter`); Chromium emits it
   as **1080 Type3 glyph-font objects** (36 per card) and a 30-card PDF is 1,152,192 B. A static 400 instance of the
   same font emits **2 Type0 fonts per page with one embedded subset** and **829,773 B (−28.0%)**. D02 ships static
   Inter cuts (400/600/700, OFL 1.1, ~24 KB TTF each) used only by the print surface.
5. **Page furniture lives in `@page` margin boxes**, not in `position: fixed`. Page numbering is therefore correct and
   cannot overprint content.
6. **The QR is generated in-repo as inline SVG** from a byte-mode, EC-M, versions 1–10 encoder, validated against an
   independent decoder (§QR verification).

Why: zero client bundle, one renderer, text-searchable A4/A5 output that the browser paginates correctly, offline on
the topology that has no server, and no dependency to license or maintain. The trade-offs rejected are the 127–432 KiB
client libraries with a second template dialect, and a server-only path that cannot print in an offline school.

## Print CSS baseline (normative for P2-D02)

The spike stylesheet is the reference implementation; these rules are the contract. All figures are measured.

### Page geometry

```css
/* emitted per document from template.page (default A4 portrait) */
@page {
  size: A4 portrait;             /* A4 | A5, portrait | landscape */
  margin: 14mm 12mm 16mm;        /* A4 portrait; bottom reserves the furniture band */
  /* the resolver emits literal strings, e.g. "Term report card · 2026" */
  @bottom-left  { content: "Term report card · 2026"; font: 7.5pt var(--print-font); color: #4b5563; }
  @bottom-right { content: "Page " counter(page) " of " counter(pages);
                  font: 7.5pt var(--print-font); color: #4b5563; }
}
```

| Template page | Size | Margins (T/R/B/L) | Content box | Baseline body |
| --- | --- | --- | --- | ---: |
| A4 portrait (default) | 210 × 297 mm | 14 / 12 / 16 / 12 mm | 186 × 267 mm | 8.5 pt |
| A4 landscape | 297 × 210 mm | 12 / 14 / 12 / 14 mm | 269 × 184 mm | 8.2 pt |
| A5 portrait | 148 × 210 mm | 10 / 9 / 12 / 9 mm | 130 × 188 mm | 7.6 pt |
| A5 landscape | 210 × 148 mm | 9 / 10 / 9 / 10 mm | 190 × 129 mm | 7.2 pt |

- Emit the rule at render time from `template.page`; do not use a global `@page`. **Remove or scope the existing
  `@page { margin: 1in; size: A4 }` in `src/styles/forms.css`** — it currently applies to every printed document.
- A4 portrait at 8.5 pt is the measured ceiling for the 11-block card: 267.0 mm, exactly the content box. 9 pt
  overflows by 8.5 mm. A 500-character comment overflows by 8.1 mm at 8.5 pt — the pack's `comment_max_length` is an
  authoring limit, not a layout guarantee.
- A5 **cannot** hold the full 11-block card: +72.5 mm at 7.6 pt, and still +9.2 mm at 5 pt. An A5 template must use a
  reduced block/column set; the engine must not promise one page for every template. A4 landscape likewise needs a
  two-column layout for a full card (+58.5 mm), and suits wide tables (broadsheets, statements).
- PDF page boxes come out at 209.9 × 297.0 mm and 148.2 × 209.9 mm (Chromium's point rounding; 0.1 mm, harmless).

### Sheet and pagination

```css
@media print {
  html, body { margin: 0; background: #fff; }
  .app-shell, .no-print, nav, button, [role="button"] { display: none !important; }

  .sheet { width: auto; min-height: 0; margin: 0; box-shadow: none;
           break-after: page; orphans: 2; widows: 2; }
  .sheet:last-of-type { break-after: auto; }

  thead { display: table-header-group; }
  tr, .row { break-inside: avoid; }
  .block, .signature-block, .keep { break-inside: avoid; }
  .block--flow { break-inside: auto; }        /* a block that contains a multi-page table */
  h1, h2, h3 { break-after: avoid; }
  p { orphans: 3; widows: 3; }
  a { color: inherit; text-decoration: none; }
  img, svg { max-width: 100%; }
}
```

- **`tfoot` is not used for totals.** It repeats on every page (measured). Totals go in a block after the table.
- **`break-inside: avoid` never wraps a table that can exceed a page.** Doing so pushed the whole statement table to
  page 2 and left page 1 blank (measured: 3 pages, page 1 header-only).
- **Multi-page documents stay in normal flow** (`.sheet.flow { display: block }`). A flex column fragments tables
  unpredictably; flex is only for the one-page card (to pin the footer).
- **One card = one sheet** is an invariant the renderer checks, not a CSS hope: after layout, compare the sheet height
  with the content box; if it overflows, apply the compact density, and if it still overflows, mark the card
  `data-overflow` and let it break (never silently ship a two-page card with a "page 1 of 1" footer).
- **Page numbering:** cards in a batch are separate documents — no `counter(pages)` (it would count the batch).
  Multi-page documents (statements, transcripts) use the margin boxes above.

### Ink and colour

- White background, `#111827` ink, `#4b5563` secondary (7.4:1 on white), `#1f2937` structural rules (0.6 mm),
  `#d1d5db` hairlines (0.2 mm).
- Tints are decorative only: `#f3f4f6` / `#fafafa`, ≤ 4% coverage. **Chrome prints backgrounds only when the user ticks
  "Background graphics"**; `print-color-adjust: exact` does not override that. The sheet must read correctly in pure
  black and white. No meaning may depend on colour: grades and levels are text (`EE`, `ME`, `AE`, `BE`), not fills.
- QR: pure black on white, no tint, 4-module quiet zone, `shape-rendering="crispEdges"`.
- Headless printing must pass `printBackground: true` or tints disappear from stored PDFs.

### Fonts

- Print surface: **static** cuts only — `Inter Print 400/600/700` (OFL 1.1), loaded with `font-display: block`,
  awaited via `await document.fonts.ready` before `window.print()`. Variable fonts become Type3: +28% file size and
  36 font objects per page (measured). Static cuts: 2 Type0 fonts per page, one embedded subset.
- Subsetting is automatic (Chromium embeds `/FontFile2` subsets); no manual subsetting step.
- RTL: `dir` comes from the pack locale (`ar` → `rtl`). Arabic falls back to a system face (measured: Tahoma +
  Segoe UI subsets). Every Latin/digit-only run (dates, marks, URLs, references) is wrapped in `dir="ltr"` or
  U+2066…U+2069 — without it the RTL card prints "Oct 2026 31".
- Labels come from the pack locale; the fallback chain is pack locale → pack default locale → `en`. Never blank.
- `font-size` floor: 8.5 pt body, 8 pt tables, 7.2 pt metadata. Below 8 pt is a fit failure, not a design choice.

### Branding and header/footer

- Header is a 3-column grid: logo 15 mm (max 18 mm) · school name, motto, contacts · term/year. Rule 0.6 mm.
- Logo as `<img>` with the school profile's data URI, `object-fit: contain`, `alt=""` (the school name is adjacent
  text). Vector (SVG) preferred; warn when a raster logo's natural width is < 240 px (≈300 DPI at 20 mm). A vector
  logo produces **0 image XObjects** in the PDF (measured).
- Footer: document id and issue date in normal flow at the end of each card; page furniture only via `@page` margin
  boxes. Do not use `position: fixed`.

### Print entry point

- Preferred: a dedicated print route that renders only the document (`/print/reports/:id`), added when D03 wires the
  route.
- Until then: render the document into a portal on `document.body`; during printing, set a `data-printing` attribute on
  `<html>` with `html[data-printing] #root { display: none }`, and clear it on `afterprint`.
  **`display: none`, never `visibility: hidden`** (measured: the hidden shell adds blank pages; `display: none`
  removes it from pagination).
- On screen the sheet is shown at 1:1 (210 mm wide) with a shadow; the print button is `no-print`.
- The print hint says "A4, 100% scale, default margins". User scale cannot be controlled from CSS.

## QR verification

Spec 03 §8.1's `verification` block is a QR code "linking to a signed verification URL"; §8.2 distributes a short
signed link by SMS. The QR carries the **full absolute URL** so a scan needs no other context.

- **Payload:** `https://<verification-host>/v1/<document-id>?sig=<base64url>`. It contains no learner name, admission
  number, marks or fee amount — a report card QR is photographed and forwarded. 68 characters → QR **version 5
  (37×37) at EC M**, 16 mm square, 4-module quiet zone (0.36 mm/module), which zxing-cpp decodes from the 150 DPI PDF
  raster. Keep the host short and the payload under ~90 characters (version 6); grow the QR to 18 mm if it does.
- **Signature:** produced by the publish service (P2-D03) over document id + snapshot hash + issued-at, stored in
  `report_card.snapshot`. D02 does not sign. A preview (unpublished) document must not carry a valid-looking QR:
  render the same block with a visible "PREVIEW — not valid for verification" label and a watermark, and either omit
  the QR or encode `<url>?preview=1` that the verifier always rejects.
- **Generation:** in-repo encoder (`src/domain/reports/qr.ts`): byte mode, EC M, versions 1–10, mask selection by the
  four penalty rules, rendered as an **inline SVG path** at print time — vector, no canvas, no PNG, no network, works
  offline. Measured: 4,644 B minified / **2,311 B gzip**; 14/14 payloads (1–200 bytes, versions 1–10, single and
  multi-block) decode to their exact input with zxing-cpp. PNG is rejected: it loses sharpness and adds an image
  XObject per page.
- **Alternative rejected:** `qrcode@1.5.4` (8.5 KiB gzip, MIT) — correct and maintained, but P2-D02 has
  `deps_install: false`, and the in-repo encoder is smaller, offline, and proven against the printed page.
- **Tests:** golden matrices for 12 payloads (D02 generates and commits them; the spike validated 14 payloads against
  zxing-cpp), a decode assertion in the test using one committed vector, and one visual snapshot of the `verification`
  block.

## Consequences

### P2-D02 must

- Build `src/domain/reports/*`: template resolution (blocks, columns, page, locale), label lookup with fallback,
  verification-URL building, and `qr.ts`.
- Build `src/components/reports/*`: one component per block type, `<ReportDocument>` with the page frame, the print
  stylesheet above, and the print entry point. `ReportDocument` is pure presentational: no data access.
- Ship static Inter print cuts plus the OFL notice (assets, not packages). If the orchestrator treats a font asset as a
  dependency, keep the variable font and accept Type3 (+28% bytes); record the choice.
- Expose fit telemetry: `data-overflow` + the measured height, so tests assert "one card = one sheet" for the pack's
  reference data.
- Prove A4 and A5 with the spike page as the visual baseline, including a long-comment case and an RTL case.
- Not touch `src/styles/forms.css` in this task; the global `@page` fix is a one-line follow-up owned by whoever owns
  that file (see Follow-ups).

### P2-D03 must

- Add the distribution path, not a renderer: print queue uses the same document; stored PDFs use headless Chromium on
  the hub/cloud with `printBackground: true`, `preferCSSPageSize: true` and `document.fonts.ready` awaited.
- Keep the server image's fonts pinned (Inter static + an Arabic face such as Noto Naskh Arabic, OFL) so batch output
  matches the browser.
- Prefer one PDF per class for bulk printing: 30 individual one-page PDFs each carry the font and card furniture
  (~312 KB each, ≈9 MB) against 1.15 MB for the 30-page file.

### Positive

- No client bundle growth beyond ~2.3 KiB of QR code and ~2.2 KiB of CSS; no dependency, lockfile or licence review.
- One renderer; the preview, the printed card and the stored PDF are the same DOM and CSS.
- Text is selectable, fonts embedded, QR vector, pages exactly A4/A5.
- Works offline on topology A; no server image for the common case.

### Negative

- The print dialog is user-controlled: scale/margins/background can break 1:1 pagination and tints. Mitigated by the
  preview, the hint and the document footer, not eliminated.
- `@page` margin boxes were measured on Chromium 140; Firefox/Safari print output would lose page numbers (content
  unaffected). The app targets Chromium (PWA, Android Chrome) but this is a compatibility edge.
- Layout fit is content-dependent and must be measured at render time.
- Arabic text extraction order is not reliable (visual shaping is correct).

## Open risks

1. **User print settings.** "Fit to page" or a custom margin letterboxes A4 → Letter or changes page count. No CSS
   control. Accept and signpost; a wrong-scale copy still carries the document id.
2. **Variable font → Type3** if static cuts are not shipped: +28% bytes, 36 font objects/page, and Type3 is rejected by
   some PDF/A profiles. Static cuts are the recommendation; the fallback is documented.
3. **Arabic in server-rendered PDFs.** A Linux hub has no Tahoma/Segoe UI; Arabic would fall back to Noto (if present)
   or tofu. Until D03 pins an Arabic font, Arabic packs should stay on the browser path.
4. **Arabic search/copy.** Glyphs and shaping are right; extraction order is neither logical nor simply reversed.
   Reports are print-first; searchable Arabic is not promised.
5. **Fit is not enforced by CSS.** A 500-character comment overflows the A4 baseline by 8.1 mm. D02 must measure and
   flag; a two-page card is a bug the renderer should surface, not hide.
6. **A5 expectations.** The full card cannot fit A5 at any legible size. Pack authors must choose an A5 block set; the
   engine should warn at pack load if a template's blocks are known not to fit.
7. **Tints.** Chrome prints backgrounds only when "Background graphics" is ticked; headless needs
   `printBackground: true`. The document must survive without fills.
8. **Chromium version drift.** The print pipeline's output (font subsets, page boxes) can shift between Chromium
   releases; visual snapshots catch it. Pin Chromium in CI and in any server image.
9. **Server image weight.** A headless print worker is ~291 MB of browser plus fonts, per hub/cloud deployment.
10. **No PDF/A, no tagged PDF.** Not required by the spec today; if a ministry or archive demands PDF/A, Type3 fonts and
    untagged text become blockers, and the decision should be revisited.
11. **Memory for large batches.** 60-page jobs were not measured for peak memory; D03 should cap batch size and stream
    per class.
12. **0.1 mm page boxes.** 209.9 mm rather than 210.0 mm; harmless for office printers, potentially relevant for
    commercial imposition.

**Revisit if:** a pack needs mixed page sizes in one document, a distribution channel requires PDF/A or tagged PDF,
or a deployment cannot rely on the browser dialog for stored PDFs.

## Follow-ups

- **P2-D02:** implement the baseline above; add the static print font cuts; add `qr.ts` with golden vectors; add the
  fit check and `data-overflow`; add print snapshots for A4/A5 (and a long-comment + RTL case).
- **P2-D03:** headless Chromium job with pinned fonts; one PDF per class for bulk; preview-vs-published QR semantics.
- **Owner of `src/styles/forms.css`:** remove or scope `@page { margin: 1in; size: A4 }` so it cannot override a
  template's page geometry; replace the `.no-print`/`button` print rules with the baseline where they overlap.
- **Owner of `ReportCardsPage`:** replace the `visibility: hidden` print hack with the D02 document when it lands
  (measured: it doubles pages on an 18 px overrun and adds blank pages for a long shell).
- **Bundle cleanup (owner of `package.json`):** remove `puppeteer` from `dependencies` (spec 06 §7). Any future server
  print worker adds it as a server-only dependency, not a client one.
