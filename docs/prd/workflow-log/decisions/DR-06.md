## Context

The project holds two modularity designs, and neither superseded the other:

- **April 2026** ([`modularity_assessment_and_improvement_plan.md:57-67`](../../../planning/modularity/modularity_assessment_and_improvement_plan.md)):
  modules own their types, schemas and migrations, and reach each other's data through `AppDataContext`. The root
  `README.md` still describes this.
- **October 2026** (spec 02 and 06, this PRD): one canonical model that "replaces … module-local types"
  (`02-domain-model.md:3-5`), schemas in `src/domain/schema` (`06:56`), and `AppDataContext` retired (`06:27`). The
  P3 work lanes then laid out `src/domain/finance/<area>` to mirror `src/modules/finance/pages/<area>`
  (`P3-finance.md:17`).

P1 built the October design and left the April machinery in place. The audit measured the result at `547cdcd`, and
re-measured M1–M3 at `7bbfadb`:

| Measure | `547cdcd` | `7bbfadb` |
| --- | --- | --- |
| Finance production files, `src/domain/finance` / `src/modules/finance` | 132 / 135 | — |
| M1: module → module imports | 34 (24 runtime) | **36** (26 runtime) |
| M2: live shared file → module imports | 61 from 11 files | 61 from 11 files |
| M3: `domain` → `data` outside the persistence ports | 11 (4 runtime) | 11 (4 runtime) |
| Unreachable module-system source files | 28, plus 13 `module.json` | — |
| Initial JS, gzip (NFR-02: ≤ 500 KB) | 2,672 KB | not re-measured |

Notes on the measurements:
- A module is a set of screens, not a capability: half of finance lives outside `modules/finance`.
- Initial JS is driven mainly by an eager glob of every module's mock data (`services/database/demoDataSeed.ts:33`).
- M1 grew by two in one pull request (#96: `reports/pages/StudentVoteheadStatementPage.tsx:18,22` into finance's
  `data/`). No guardrail could stop it, because the existing checks cannot see these imports and do not run on pull
  requests into `consolidation`.

## Options

| Question | Options | Recommended |
| --- | --- | --- |
| Layout | **A** layered, as today: shared `src/domain`, modules as screens, boundaries enforced · **B** vertical slices over a shared kernel: a module owns its bounded context | B |
| Unreachable module machinery | wire all · wire the parts that fit B, delete the rest · delete all | wire the parts that fit B |
| Cross-module calls | typed imports through `public.ts` · runtime `ServiceRegistry` | `public.ts` |
| NFR-02 startup budget | ratchet, then a hard gate once under · hard gate now · revise the number | ratchet, then hard gate |
| Tests importing other modules | allow test doubles · allow nothing | allow test doubles, for now |

Layout B is the only one in which "a module" means the capability, which is the stated goal: each module self-reliant,
and every new module built the same way. Spec 02's real rule (one definition per entity, no denormalised copies)
survives under B; only the folder an entity is defined in changes. Option A was cheaper, but it leaves adding a module
as a set of edits to shared files.

## Decision

1. **Layout B.** A module owns its bounded context: screens, hooks, domain code, entity schemas and migrations. It
   contributes them to one composed registry.
   - **The kernel stays in `src/domain`.** It holds ids, money, calendar, sequences, the common schema shapes, the
     shared entities (institution, people, class groups, enrolment, attendance), and the shared engines (workflows,
     the report-document engine, country and curriculum packs).
   - A context with one owning module moves into that module.
   - A context several modules need either stays in the kernel or gets an owner with a public surface, decided per
     context (P7-F03).
2. **One manifest per module: `module.json`,** loaded by `ModuleMetadataLoader`. It holds id, name, version,
   dependencies, `provides`, schemas, permissions and feature flags. `moduleDefinition.tsx` keeps only what needs React
   (icons, navigation components, lazy pages, contributions that reference components). No field is declared in both.
3. **Machinery.**
   - **Wire:** `module.json` with `ModuleMetadataLoader`; `ModuleExports`, as the `public.ts` contract; lifecycle hooks
     through `convertToLoadedModule`; and module enable/disable (`useModule`, `moduleManagementService`,
     `moduleConfigService`) once the cross-module edges are fixed.
   - **Delete:** `ServiceRegistry`, `useService` and `registerServices`; `dynamicModuleLoader`; `ModuleBundler`,
     `useLazyModule`, `useModuleLoadingPerformance`, `ModuleLoadingProgress` and `ModularSystem`; `moduleOrder`;
     `moduleCollectionRegistry`; the `hooks/data` barrels; `pageComponentResolver`; `modules/portal/examples`; and the
     `src/core/index.ts` barrel.
4. **Cross-module calls** go through typed imports of `modules/<x>/public.ts` only, with no runtime service lookup.
   This keeps every cross-module dependency visible to the CI ratchet.
5. **One composition root.** `src/core/moduleRegistration.ts`, fed by the manifests, is the only shared code that names
   modules, apart from the router (`routing/pageLoader.ts`, `routing/routeConfig.ts`).
6. **Tests, interim policy:** a test may import another module's test doubles, but no other internals of another
   module. The policy ends when the generic doubles move to shared test support (P7-E03).
7. **NFR-02:** CI reports initial JS and fails when it grows (a ratchet). It becomes a hard 500 KB gate once the
   number is under 500 KB. The PWA precache and route-chunk sizes are reported alongside.
8. **`ARCHITECTURE.md` invariant 3** ("`AppDataContext`, routing, module registry: additive changes only") is amended:
   P7 tasks may change these, under P7's tests and ratchets.
9. **Tracking:** new requirement NFR-09 (PRD 1.1) and phase P7.

## Consequences

Positive:

- A module becomes the capability. Adding one means adding a folder; removing one means deleting it.
- Boundaries become numbers that CI ratchets down (M1–M3), instead of conventions nobody checks.
- At boot, the composition root reads static JSON manifests, not every module's chunk.
- The dead April machinery stops misleading contributors; the parts worth keeping get a real job.

Negative, and mitigations:

- **Moving contexts is large:** 132 finance files, more for academics. It comes after the composition root and the
  ratchet exist, one context per task. The DDL must be identical before and after (schema dump compared), so no data
  migration is needed and schools are not disrupted.
- **Done tasks' `files` fields in `tasks.json` will name old paths.** They are history and stay as they are.
- **Server-safe domain code will sit next to React code in module folders.** A lint rule keeps
  `modules/<x>/domain/**` free of UI imports (P7-A02).
- **Module disabling becomes real.** "Optional" dependencies that the code imports unconditionally must be fixed
  first (P7-D lane before P7-B wiring of enable/disable).
- **The closed `EntityName` union must stay closed** once it is derived from module contributions (P7-F01).

Revisit if:
- per-school builds and independently developed modules turn out not to be needed: stop after P7-W4 and stay on layout
  A plus the boundary rules;
- a composed registry cannot keep `EntityName` closed and type-safe.
