# DR-02 — Sync engine: SQLite↔Postgres against PouchDB↔CouchDB

**Date:** 2026-10-23
**Status:** accepted
**Decided by:** implementer P4-A01, for P4-A02, P4-A03 and P4-B01
**Supersedes:** nothing. Realises spec 06 §3 and the P4 design commitments.

## Context

P4 must let many staff devices share one school while offline or online (spec 06 §3).
The phase commitments are fixed before the engine is chosen:

- one local engine (SQLite) and one server engine; the other providers are removed
  after DR-02 (`docs/prd/phases/P4-sync-and-security.md`);
- conflict policy per entity: append-only financial/attendance events, cell-level
  merge for marks, field-level LWW with a conflict log for profiles, server-allocated
  sequences with device blocks;
- permissions evaluated identically on client and server.

P1 already put every entity behind one repository over one SQLite adapter
(`src/data/**`): one `entitySchema`, one `encodeRow`/`decodeRow` codec, one set of
`guardsFor`/`guardsForRemoval`, one `writeAuditEvent`, one `transaction`. The open
question for P4-A01 is therefore narrow and testable:

> Can that single domain layer sit on SQLite on the device and on the *server engine*
> unchanged — or does a sync candidate force a second implementation of the domain?

The spike compares two candidates and measures what each costs. Code, commands and
raw results: [`spikes/sync/`](../../../../spikes/sync/README.md) and
`spikes/sync/results/*.json`.

## Options

### A. Canonical repository on SQLite (device) with SQLite *or* Postgres (server)

The existing repository, schemas, codec and guards, plus what sync genuinely needs:
an outbox recorded **in the same transaction as the write** (`repository.transaction`),
a fixed-width HLC (`wall(15):counter(6):device`, so a string compare is the total
order in JS and in SQL), a change envelope carrying the changed `fields` and a
per-field `base` clock, and our own merge policies as pure functions
(`spikes/sync/src/policies.ts`). The server backend is a parameter (`'sqlite' |
'postgres'`); the device is always SQLite.

Postgres was measured for real (PostgreSQL 18.1, `postgres://postgres:postgres@localhost:5432/postgres`)
through the harness that already exists: `createSqliteAdapter(new PostgresDriver(client, schema))`,
the same `CoreSqliteAdapter` the device uses. That is the point of the candidate — the
backend is a driver, not a dialect fork.

### B. PouchDB↔CouchDB

A document store with its own replication and conflict model, with the same merge
policies run after replication resolution (`spikes/sync/src/pouchSync.ts`).

No Docker Desktop on this machine — `docker ps` fails on
`//./pipe/dockerDesktopLinuxEngine` — so what was measured is
**PouchDB↔PouchDB local replication** (`pouchdb-node`, LevelDB in temp directories).
The CouchDB wire, `_changes` and filtered replication are declared unmeasured; they
are the part people actually deploy, and this is a real limitation of the evidence
below, not a detail.

## Measured evidence

Three kinds of number: **statements** (engine round trips, from
`countStatements(adapter)` wrapping the adapter's driver — one counter serves SQLite
and Postgres because both build `createSqliteAdapter(driver)`), **bytes** (JSON
envelope, snapshot and document sizes), and **latency** (vitest on a loaded Windows
dev box — the tails are wide and are quoted as measured, not smoothed).

### A. Canonical — the same work costs the same on both engines

| Work | SQLite | Postgres |
| --- | --- | --- |
| statements to bootstrap (DDL + 68 fixture rows) | 998 | 998 |
| statements to serve the first pull (68 rows) | 138 | 138 |
| statements for one accepted change | 28 | 28 |
| statements for 20 changes in one push call | 560 | 560 |
| statements for a pulled batch | 42 (20 rows) | 82 (40 rows) |
| merge (pure policy, no database) | 2.84 µs mean | — |
| two devices editing one field | 1 conflict logged | — |

**The four identical counts (998 / 138 / 28 / 560) are the headline result**: the same
domain code performing the same work issues the same statements on both engines.
Pulled batches decompose exactly as `2 × rows + 2` on both — 138 = 2·68 + 2,
82 = 2·40 + 2, 42 = 2·20 + 2. Pushes are linear at 28 per change.

Latency, for the link budget:

| Operation | p50 | p95 |
| --- | --- | --- |
| local write through the repository, with its outbox entry (SQLite) | 7.9 ms | 10.9 ms |
| one change pushed to a SQLite server | 8.1 ms | 30.5 ms |
| one changed row pulled and folded in (SQLite) | 3.4 ms | 15.2 ms |
| one change accepted by a Postgres server | 23.4 ms | 31.9 ms |
| a bare `SELECT 1` on Postgres (the round trip the numbers rest on) | 0.285 ms | 0.448 ms |
| 20 changes in one push call to Postgres | 561.6 ms | — |
| a pull carrying 40 snapshots from Postgres | 120.0 ms | — |

An accepted Postgres change is **82× a bare round trip** (23.4 ms against 0.285 ms) for
28 statements inside a transaction. A naive 30-round-trip estimate is 8.6 ms, so most of
the measured time is per-statement parse/plan and local-socket overhead, not the round
trip itself. This is a *local* server: a LAN or cloud link adds its own latency on top of
30 round trips per change, which is why batching matters (P4-A02). The counter checker:
`paymentsHeld = 81`, i.e. the bench's writes all landed.

Latency varies widely between runs on this machine (the same operations moved by 2–3×,
and the PouchDB replication by an order of magnitude); the **statement counts do not** —
they are properties of the code and are identical run to run. Treat the latencies as a
shape for the link budget, and the statement counts as the result.

Bytes per change (JSON, uncompressed), from `results/bench-bytes.json`:

| | append-only (payment) | cell (mark) | profile (learner) |
| --- | --- | --- | --- |
| patch envelope (one field) | 272 B | 269 B | 272 B |
| whole-row create envelope | 1113 B | 1115 B | 1617 B |
| snapshot (row + clocks) | 1625 B | 1660 B | 2525 B |
| the row alone | 712 B | 710 B | 1054 B |

A patch is ~270 B whatever the entity, so a delta is cheap and constant. The first
pull is 68 snapshots = **87 643 B** (mean 1289 B).

### B. PouchDB — the storage unit is the contradiction

| Measurement | Value |
| --- | --- |
| Pouch document for the same 6-field learner row | 658 B |
| canonical whole-row envelope, same row | 327 B |
| canonical changed-fields envelope, same row | 228 B |
| document ÷ whole-row envelope | **2.89** |
| a one-field edit, as a whole document | 649 B = **98.6 %** of the whole-row create |
| 100 concurrent same-row creates on two replicas | 100 conflicts |
| winner agrees with the HLC | **50 / 100** |
| `bulkDocs` atomicity | not atomic (partial writes observed) |
| put one document, on its own | p50 13.66 ms, p95 59.6 ms |
| one document at a time, 20 in sequence | p50 1.474 ms, p95 4.35 ms |
| 20 documents in one `bulkDocs` | p50 7.102 ms, p95 21.8 ms |
| first replication, 50 documents | p50 165.5 ms |
| next replication, 130 documents | p50 410.3 ms |
| documents held / as JSON | 180 / 130 060 B |

The load-bearing finding is the conflict model, not the latency. PouchDB resolves a
conflict on the **whole document**, and its winner is chosen by the **revision tree** —
it agreed with the HLC ordering only **50 %** of the time, i.e. it is a coin toss with
respect to our policy. Two replicas that created the same row offline produce a
conflict 100/100, so *every* concurrent create pays, and a decision still has to be
made afterwards by our own policy. `bulkDocs` writing partially breaks the
"one change = one transaction" invariant the repository guarantees.

For the two device latencies the tails are heavy (putting one document on its own has
p50 13.66 ms against p95 59.6 ms, and was worse in earlier runs) — the machine was loaded
and LevelDB compacts. The replication figures are single-sample p50s and moved by an order
of magnitude between runs (165 ms against 1804 ms for the same 50 documents). They are
indicative, not a benchmark.

## Where a fork is forced

This is the question P4-A01 exists to answer, and the two candidates answer it
differently.

**A. Canonical — no fork of the domain layer.** The same repository, schema, codec,
guards and audit path ran unchanged on SQLite and on Postgres, and issued identical
statement counts for identical work. What sync must **add** is additive, not a second
domain:

1. **An apply verb.** `create`/`update`/`remove` stamp the *local* clock and sequence.
   Applying a remote change needs a verb that takes the change's own `hlc` and per-field
   `base` and does not re-stamp them (`applyIntent` in `spikes/sync/src/canonicalSync.ts`).
2. **Deep imports.** `guardsForRemoval` and `RemoveOptions` are not re-exported by
   `@/data/repository`; the spike imports them from the module path. Either re-export
   them or have the apply verb own removal guards.
3. **Sequence allocation.** A pull applies rows without advancing
   `repository.currentCommitSequence` (it is left at 0), so the next local write reuses
   sequence 1 — measured directly as `COUNT(commit_sequence = 1) = 2`. Commit-sequence
   allocation must move to the server — which is exactly P4-A03's server-allocated
   sequences with device blocks.
4. **No `ChangeEvent` on pull.** The repository emits change events for local writes
   only; a pulled row is written behind that path, so live queries (`useQuery`) will not
   refresh on sync unless the apply verb emits or invalidates. P4-A02 owns this.
5. **Apply order.** The FK-safe order is today a test fixture (`SEED_ORDER`). Remote
   changes arrive in arbitrary order and Postgres enforces foreign keys for real, so the
   sync layer must order or defer them.

**B. PouchDB — the fork is forced at the storage unit itself.** None of the per-entity
policies in the P4 commitments can be expressed on a document store:

1. **Cell-level merge for marks is lost.** The conflict unit is the whole document, so
   two devices editing different cells of one mark produce an unresolvable document
   conflict; the cell identity the domain relies on has to be re-derived after
   replication — and two surviving mark documents mean two rows, not one merged row.
2. **Field-level LWW is a fiction.** Different-field edits still conflict, so LWW has to
   run after the fact over the conflict pair, not instead of it.
3. **The HLC is not the decider.** PouchDB's winner came from the revision tree and
   agreed with our ordering 50/100, so our clocks must re-decide anyway — the store
   supplies no useful ordering.
4. **No server guard.** There is no server-side validation or guard rejection: the
   repository's guards and the "permissions evaluated identically on client and server"
   commitment would have to be re-implemented in the replication path.
5. **The clock travels anyway.** Because the document is the row, a one-field edit costs
   98.6 % of a whole-row create (649 of 658 B), and the per-field clock and base must be
   carried *inside every document* to be recoverable — the envelope the canonical
   candidate needs is not avoided, it is embedded in a larger object.
6. **`bulkDocs` is not atomic**, so a partial batch can leave the store half-applied.

## Decision

Adopt **option A: the canonical repository on SQLite (device) with SQLite or Postgres
(server), our own outbox, HLC, envelope and per-entity merge policies.**

Rationale: the domain layer is the asset P1 built, and it demonstrably does not fork —
identical statement counts on both engines for identical work. PouchDB does not remove
the work the canonical candidate does (the HLC, the per-field clocks, the guards, the
envelope); it only puts a whole-document, revision-tree conflict model underneath it,
which cannot express cell-level marks or field-level LWW and rejects any concurrent
write as a conflict. The feed the store would need is already in the write path.

The decision covers the P4 commitments directly: append-only financial/attendance
changes are the same code path in both candidates and are cheapest on A (a 270-byte
patch); cell-level marks and field-level LWW with a conflict log are expressible only
on A; server-allocated sequences are required on A by the measured sequence collision.

## Consequences

- **P4-B01 (hub skeleton):** the hub holds the same repository server-side, over
  Postgres or SQLite, and exposes apply/change-log operations to the sync layer. The
  statement-count identity is the acceptance evidence that it runs domain services
  unchanged.
- **P4-A02 (protocol):** owns the change log and cursor, HLC versions, scoped replicas,
  the per-entity policies and the conflict-log UI. It must produce a `ChangeEvent` (or
  an invalidation) when it applies a pulled row, or live queries go stale.
- **P4-A03 (sequences):** confirmed necessary by the measured double-sequence-1. Server
  allocation with device blocks replaces the client-side commit sequence.
- **Latency budget:** a Postgres change is ~23 ms on a *local* socket for 28 statements;
  over a LAN it is dominated by round trips, so P4-A02 must batch (`acceptBatch`) —
  the benchmark pushes one change per call, and 20 changes in one call cost 561.6 ms,
  i.e. 28.1 ms each, not a saving.
- **Byte budget:** a patch is ~270 B; a cold device's first pull is 87.6 KB for 68 rows
  of the current schema, before compression.
- **CouchDB is not adopted**, so its wire cost, filtered replication and server
  validation are deliberately not measured further.
- The Phase-4 commitment "the other providers are removed after DR-02" now has a named
  target: the RxDB/Pouch-style provider paths retire in favour of the one repository.

## Spike evidence

`npx vitest run spikes/sync` — 43 cases:

- `policies.test.ts` 16/16 — the pure merge policies: append-only refusal to
  re-order an accepted financial event, cell-level marks, field-level LWW, the
  conflict log, and the HLC total order.
- `canonical.offline.test.ts` 10/10 — offline writes on two devices, push/pull,
  merge per entity policy, conflict recording, idempotent re-apply.
- `canonical.postgres.test.ts` 5/5 — the same behaviour with the server on Postgres.
- `pouch.offline.test.ts` 8/8 — replication, post-replication resolution and the
  whole-document conflict behaviour measured above.
- `bench.test.ts` 4/4 — the bytes, latency and statement counts in
  `results/bench-sqlite.json`, `bench-postgres.json`, `bench-bytes.json`,
  `bench-pouch.json`, `pouch-bytes.json`, `pouch-update-bytes.json`,
  `pouch-conflicts.json`.

`npx tsc -p spikes/sync/tsconfig.json --noEmit` exits 0. That config exists because the
root `tsconfig.json` includes only `src/**`; it aliases `@/*` back to `src/*` so the
spike compiles against the real repository. No new dependency was added (`pg` and
`pouchdb-node` were already in the lockfile), and nothing under `src/**`,
`package.json`, `tsconfig.json` or `vitest.config.ts` was modified.

### Not measured (stated plainly)

- **CouchDB.** Docker is not running, so candidate B is PouchDB↔PouchDB local
  replication; the HTTP wire, `_changes` and filtered replication are unmeasured.
- **Two concurrent server processes** against one Postgres; the concurrent writer here
  is a second node in one process.
- **Real clock skew, compression, TLS and a real LAN/3G link.**
- **Browser storage** — SQLite-WASM/OPFS and IndexedDB; the spike runs SQLite on Node.
- **Growth**: outbox, cursor and change-log size over time; guard cost at scale.
- **`acceptBatch`**: the benchmark pushed one change per call.

## Follow-ups

- **P4-B01:** stand up the hub on the repository; expose `applyIntent`/`changesSince`
  and the change log. Confirm the Postgres statement counts match the spike's.
- **P4-A02:** implement the change log, cursor, HLC, scoped replicas, per-entity
  policies and conflict log; emit `ChangeEvent` on apply; batch pushes; re-export or
  absorb `guardsForRemoval`; make the pull emit or invalidate for live queries.
- **P4-A03:** server-allocated sequences and device blocks, driven by the
  double-sequence-1 finding.
- **P4-D03:** the health page reads last-sync lag and outbox depth — the numbers these
  benchmarks produce are the shape it should show.
- **Optional:** if Docker becomes available, measure the CouchDB wire so candidate B's
  server cost is known rather than assumed; it does not change the decision.
- **Deferred measurement:** real devices (browser SQLite-WASM/OPFS, IndexedDB), a real
  link, and two concurrent server processes — all of which need hardware or a network
  this machine does not have.
