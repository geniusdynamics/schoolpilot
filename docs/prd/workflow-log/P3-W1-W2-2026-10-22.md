## The frozen interfaces (what later waves must use)

- `@/domain/money` — hold `Money` (integer minor units + currency), **never a major-unit number**.
  `add`/`subtract`/`sum` are exact and refuse mixed currencies; `allocate` is the only splitter.
- `@/domain/sequences` — every document number comes from here. **Do not invent one.**
- `@/domain/finance/ledger` — every posting goes through the engine; corrections are reversals.
- `@/domain/finance/allocation` — every split of a payment goes through the plan.
- `@/domain/finance/feeItems` — GL mapping and vote-head priority live here.

## Findings worth carrying forward

1. **Two of these five modules cannot be used in production until a migration applies their DDL.**
   The sequence tables and the ledger tables are defined in their modules and applied by
   `ensureSequenceSchema` / `ensureLedgerSchema`, but the repo's `src/data/migrations` framework
   migrates *legacy data*, not schema, and there is no schema-migration path for a module-owned
   table. Both tasks took the same posture and both said so plainly. **This is now a phase-level
   blocker for anything that actually writes money**, and it needs an owner decision: a schema
   migration path, or moving these tables into the canonical registry.

2. **A real bug found while migrating `formatKES`.** `admissionService.nextAdmissionNumber` reads at
   most 500 learner rows and then computes the next number, so **admission numbers repeat once a year
   passes 500 learners**. The invoice path has the same shape in memory. Both should call the
   sequences module. Reported, not fixed — callers are other tasks' files.

3. **The demo school's grading scale was already repaired in P2** so the banded path could be proven,
   but the underlying gap remains: the canonical `grading_scale` cannot store a band's upper-bound
   convention, so a school on any shipped pack still cannot award a band. Still outstanding.

4. **The page-route guard earned its place in production.** P3-B01's agent reported that it failed the
   new fee-items page as unreachable until the route entry and hub tab were added. That is the guard
   doing exactly what it was built for, on the first task to add a page after it landed.

5. **Load flakes, not regressions.** Three separate agents hit a load-sensitive test
   (`AuthLoginRedirect`, a 5 s first-render wait) under the four-agent load; each re-ran and passed,
   and the wave gate itself passed first time. Recorded so it is not mistaken for a real failure later.

## Known gaps carried out of these waves

- No schema migration path for module-owned tables (the blocker above).
- `fee_item` has no `description` and no per-item amount; the task card asked for both and neither is
  representable. Adding either needs a new column plus the repository's additive column sync or a
  numbered migration — a shared-interface change, reported rather than made.
- The chart of accounts is not modelled, so the ledger's account codes are its own choice behind a
  mapping seam, and the fee-item GL directory is an optional port.
- A refund debits *refunds payable* and credits the payout channel — a stated policy, not a spec
  fact, flagged for the real chart to overturn.
- `allocate` is exact, but `admissionService` and the in-memory invoice numbering still bypass the
  sequences module.
