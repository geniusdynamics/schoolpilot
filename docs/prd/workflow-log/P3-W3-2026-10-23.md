## Findings worth carrying forward

1. **The schema-migration path composes with the legacy migrations instead of replacing them.**
   One ledger, two version bands: data migrations own 1–99, module schemas own 100–199. The
   migrations carry **no copied DDL** — they import the modules' own `SEQUENCE_DDL`, `LEDGER_DDL` and
   `RECONCILIATION_DDL` and derive the drops from the same text. Two small framework extensions make
   the bands coexist (a runner may declare versions it knows but does not run; a rollback undoes only
   what its runner owns). **The rollback is proven against enforced foreign keys**, with the test
   first asserting the connection really refuses a delete a child row would violate — so the rollback
   assertion cannot be vacuous.

2. **The owner's reporting warning was correct, and the honest answer is "retain them all".**
   A page-by-page, feature-by-feature comparison found **no** legacy finance report fully covered:
   the trial balance lacks an account-type filter and search; the income statement lacks a
   previous-period comparison and margin; the balance sheet lacks category filters, working capital
   and the debt ratio; the cash book lacks search and a payment-method column; the day book, journal
   register and per-account ledger have no replacement at all; and the main reports view with the CFO
   KPI table is hard-coded. Nothing was retired, and the document says exactly what is missing for
   each — which is what the owner asked for so they can verify by hand.

3. **Two things found in passing that matter more than they look.** First, **seven finance pages pass
   `exportable` to `DataGrid`, which has no such prop** — so those pages have no working export at
   all, and the new hub's CSV is a genuine gain rather than a duplicate. Second, the finance
   deprecated routes redirect to the **placeholder** hubs, not the new accounting hub, so retiring
   the books later means repointing those targets first.

4. **The `formatKES` migration silently dropped a `GAP` marker** from `OverdueReport.tsx`, and CI
   caught it. The canonical-data guard requires any file still reading legacy collections to carry
   the marker naming the missing canonical entity. A money-formatting change is not where you expect
   a data-access guard to fire, which is exactly why it is worth having.

5. **The load-flake tax is real and now familiar.** Three agents this wave hit the same
   load-sensitive integration tests (the setup wizard's 5 s first render, `AuthLoginRedirect`) and
   each passed on re-run; the wave gate itself passed first time. Recorded so it is not mistaken for
   a regression later.

## Known gaps carried out of this wave

- **The canonical `user` row still does not exist**, so a payment's `cashier_user_id` is a foreign key
  the screen cannot write, and the cashier identity is supplied by the shell. The same gap broke
  report publishing in P2 and the fee-schedule editor's workflow actor. **This is now the single most
  repeated blocker in the project** and deserves its own task.
- `invoice_line` has no `fee_schedule_id`, so a bill can resolve the version it was priced from but
  cannot pin it (reported for P3-C01).
- The pack `grading_scale` still cannot store a band's upper-bound convention, so a school on any
  shipped pack cannot award a band.
- No canonical budget entity, so budget-versus-actual takes a stored figure the caller supplies.
- The 500-learner admission-number bug (numbers repeat past 500) is still unfixed; callers should use
  the sequences module.
- `fee_item` still has no `description` or per-item amount.
