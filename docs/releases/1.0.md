## What 1.0 is

SchoolPilot is a local-first school management system for multi-curriculum schools. It runs in the
browser on a school's own device (SQLite-WASM/OPFS), can put its database and API on a LAN hub, and
covers the school year from admission to promotion:

- **Academic core:** academic years and periods, levels, class groups, subjects, timetable, teaching
  groups, enrolment.
- **People:** learners, guardians and their links, staff, identifiers, consent fields the schema
  records.
- **Attendance:** registers and marks, leave-outs, conduct and health records.
- **Finance:** fee structures and billing runs, invoices, payments and receipts, allocation,
  statements, credit notes, the ledger and its reports, accounting exports.
- **Assessment:** grading schemes, marks, report cards, published reports, promotion runs.
- **Portal:** a guardian/learner PWA for balances, pay links, published reports, attendance, notices
  and consent.
- **Packs:** curriculum, country and payroll data as versioned packs, with a schema and a vector
  runner. The shipped packs are drafts; each `pack.json` lists what is unverified.
- **Integrations:** KEMIS/KNEC registration exports, SMS/WhatsApp/email providers behind an outbox,
  accounting journal exports (QuickBooks, Xero, Odoo, ERPNext).
- **Extensions:** a documented plug-in SDK and manifest. The host does **not** load third-party
  plug-ins yet; a plug-in can be built and tested, not installed by the app.

The hub serves `/health`, `/.well-known/schoolpilot-hub` and `/api/**`; it does **not** serve the
browser application. Staff still open the app from its own host.

**Upgrade path:** back up first, install the tagged release, run the migrations, then check the
health page and one golden path. A restore from the pre-upgrade backup is the rollback. The P0-era
data migration is covered by the migration suite; it has **not** been verified as a 1.0 upgrade on a
real P0 database, so the release checklist keeps that box open.

## Known issues and limitations at 1.0

- **Packs are drafts.** Every shipped curriculum pack is `verification: draft`; the unverified items
  are in each `pack.json`. A curriculum officer must review them before a school relies on the
  assessment rules.
- **Translations are drafts.** sw, fr, pt and ar are complete against English but not reviewed by
  native speakers; rw is partial. The payroll pack's statutory data has no accountant sign-off.
- **Guardian-only login.** A login whose only role is a guardian cannot reach module routes in this
  build. The portal is scoped correctly in its data layer, but a school needs a staff login linked
  to the guardian until the role/permission wiring changes.
- **No payment provider is configured.** The fees page shows that state; a live pay link needs a
  provider integration and credentials.
- **The plug-in SDK is not host-wired.** No load-time validation, install-time compatibility check,
  slot rendering or hook publishing in the host yet.
- **The hub does not serve the app.** It is the server side and the API.
- **Portal performance budget not measured.** Lighthouse mobile, 3G, a 2–3 GB Android device and PWA
  offline are unmeasured; the commands are in `docs/architecture/portal-performance.md`.
- **Deployment steps.** Single-device, hosted and Raspberry Pi were not run end to end here; the
  guides say so.
- **Open owner decisions:** Ethiopian locales default to the Ethiopian calendar (`am-ET`, `en-ET`,
  `ti`); the public application wizard cannot pass step 1 (pre-existing). Both are recorded in the
  phase logs and need a product decision, not a silent default.
- **Video walkthroughs** are scripts only; the recordings are outstanding.

## Stable channel and LTS policy (proposed — owner approval required)

This is the policy the release would publish; it is not in force until the owner signs it.

- **Stable channel:** only tagged releases (`v1.0.0`, `v1.0.1`, …) with green CI and a GitHub release
  with checksums. A school never installs a branch head.
- **Patch releases:** bug and security fixes only; no schema-breaking change without a migration and
  release notes. Security fixes take priority over features.
- **Support window:** 12 months of security fixes for the 1.0.x line from the 1.0.0 tag, with upgrade
  guidance for 6 months after the next minor. Extending it is an owner decision, made in public.
- **LTS:** 1.0 is the first LTS line; pre-1.0 versions are not supported. A 2.0 would start a new
  line and the 1.0 window would be announced at least 90 days before it closes.
- **Upgrade:** backup → tagged install → migrations → health and one golden path → keep the backup
  until the school signs off the upgrade. Rollback is the backup.
- **End of life:** announced at least 90 days ahead in `CHANGELOG.md` and the release notes; no
  silent end of support.
