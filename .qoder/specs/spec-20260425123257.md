# Spec: TypeScript Module Augmentation for AppDataType

## Context

The SchoolPilot3 codebase has a centralized `AppDataType` monolith in `src/core/types/app-data.ts` containing ~85 hardcoded collection properties. Types are imported from every module (administration, academics, finance, inventory, library, etc.) into the core, creating a tight coupling. When new collections are added, developers must manually edit the core type file.

Meanwhile, the runtime collection discovery system (`moduleCollectionRegistry.ts` + per-module `collectionConfig.ts`) already auto-discovers collections at runtime. The gap is compile-time types: TypeScript needs to know about collections at compile time, but the registry only knows at runtime.

This spec implements **TypeScript module augmentation** (declaration merging) so each module can extend `AppDataType` and `AppDataContextType` without touching core files.

## Architectural Vision: Frappe-Style Decoupling in TypeScript

Frappe achieves zero compile-time coupling between modules through a metadata registry: DocTypes are referenced by string name (`"Customer"`, `"Warehouse"`), and a central `get_meta("Customer")` resolves schema at runtime. Modules never import each other's classes.

In TypeScript, we cannot fully replicate this because types are erased at runtime. However, we can achieve the **compile-time equivalent** using TypeScript's declaration merging:

| Frappe Pattern | TypeScript Equivalent |
|----------------|----------------------|
| `frappe.get_meta("Customer")` | `keyof AppDataType` — registry of all known collection names |
| `frappe.get_doc("Customer", id)` | `useAppData().customers` — typed access through augmented interface |
| String-based DocType references | `declare module '@/core/types' { interface AppDataType { customers: Customer[] } }` |
| Runtime schema registry (`tabDocType`) | `moduleCollectionRegistry.ts` — already exists |
| Module self-registration | Per-module `appDataAugmentation.ts` + `collectionConfig.ts` |

**Key insight:** TypeScript's `declare module` augmentation IS the compile-time metadata registry. Each module "registers" its types by augmenting the central interface, without the central file importing from the module. This mirrors Frappe's pattern where modules register DocType metadata without other modules importing their code.

## Intended Outcome

- `AppDataType` becomes an extensible interface that modules augment (compile-time metadata registry)
- Each module owns its slice of `AppDataType` and `AppDataContextType` (self-registration)
- Adding a new module requires zero changes to core type files (zero compile-time coupling)
- Full type safety is maintained across `useAppData()`, loading states, and CRUD operations
- `any[]` properties that were previously untyped get proper types via module augmentation
- The barrel (`@/core/types`) only exports core-defined types, not module-specific types (clean hub)

## Design Decisions (Confirmed with Mr GENIUS)

1. **Augment both `AppDataType` and `AppDataContextType`** — modules declare their data arrays AND their CRUD operations
2. **Properly type all `any[]` properties** — use the opportunity to replace `any[]` with actual entity types
3. **Separate `appDataAugmentation.ts` per module** — cleaner separation from entity type definitions
4. **Two parallel systems** — compile-time type registry (declaration merging) + runtime schema registry (existing `moduleCollectionRegistry.ts`)

## The Two-System Architecture

TypeScript types are erased at runtime. To replicate Frappe's pattern, we need:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         COMPILE-TIME (TypeScript)                           │
│                                                                             │
│  ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐       │
│  │  Core Types     │◄────│  Module A       │     │  Module B       │       │
│  │  (empty         │     │  appDataAug.    │     │  appDataAug.    │       │
│  │   interfaces)   │     │  declares:      │     │  declares:      │       │
│  │                 │     │    students     │     │    banks        │       │
│  │  AppDataType{}  │     │    addStudent   │     │    addBank      │       │
│  │                 │     │    updateStudent│     │    updateBank   │       │
│  └─────────────────┘     └─────────────────┘     └─────────────────┘       │
│           ▲                          ▲                    ▲                │
│           └──────────────────────────┴────────────────────┘                │
│                         Declaration Merging                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼ Types erased
┌─────────────────────────────────────────────────────────────────────────────┐
│                          RUNTIME (JavaScript)                               │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │              moduleCollectionRegistry.ts                            │   │
│  │  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌────────────┐ │   │
│  │  │ collection  │  │ collection  │  │ collection  │  │ collection │ │   │
│  │  │ Config A    │  │ Config B    │  │ Config C    │  │ Config D   │ │   │
│  │  │ (aliases)   │  │ (aliases)   │  │ (aliases)   │  │ (aliases)  │ │   │
│  │  └─────────────┘  └─────────────┘  └─────────────┘  └────────────┘ │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Compile-time:** Modules augment `AppDataType` via `declare module '@/core/types'` — no imports needed, no circular dependencies.
**Runtime:** `moduleCollectionRegistry.ts` aggregates `collectionConfig.ts` exports — already works, no changes needed.

## Implementation Plan

### Step 1: Refactor Core `src/core/types/app-data.ts`

**What to change:**
- Convert `AppDataType` from `type` alias to `interface` (required for declaration merging)
- Remove ALL cross-module imports (~60 lines of imports from `../../modules/*/data/types`)
- Strip `AppDataType` down to only truly universal core properties: `schoolDetails`, `users`, `roles`
- Keep `AppDataLoadingStates` as a mapped type over `AppDataType` — it auto-expands with augmentation
- Strip `AppDataContextType` down to base properties: loading states, raw data, DB management, and cross-domain helpers (`getStudentDetailsById`, `getStudentFinancialDetailsById`)
- Remove ALL module-specific CRUD operations from `AppDataContextType` (~60 operations move to module augmentations)

**What stays in core:**
```typescript
export interface AppDataType {
  schoolDetails: SchoolDetails | null;
  users: User[];
  roles: Role[];
}

export type AppDataLoadingStates = {
  [K in keyof AppDataType]: boolean;
} & { all: boolean };

export interface AppDataContextType extends AppDataType {
  loading: AppDataLoadingStates;
  rawInitialData: any;
  initializationError?: Error | null;

  triggerClearRxDB?: () => Promise<void>;

  getStudentFinancialDetailsById: (id: string) => Promise<any | null>;

```

### Step 2: Create Module Augmentation Files

Create `src/modules/<module>/data/appDataAugmentation.ts` for each module. The pattern:

```typescript
// ABOUTME: TypeScript module augmentation for <Module> collections in AppData
// ABOUTME: Extends AppDataType and AppDataContextType with module-specific properties
// ABOUTME: This is the compile-time equivalent of Frappe's DocType self-registration

import type { EntityType1, EntityType2 } from './types';

declare module '@/core/types' {
  export interface AppDataType {
    entityType1s: EntityType1[];
    entityType2s: EntityType2[];
  }

  export interface AppDataContextType {
    addEntityType1: (data: Omit<EntityType1, 'id'>) => Promise<EntityType1>;
    updateEntityType1: (id: string, data: Partial<EntityType1>) => Promise<EntityType1>;
    deleteEntityType1: (id: string) => Promise<void>;
  }
}
```

**How this mirrors Frappe's pattern:**

```typescript
// Frappe (Python): Module A references Module B by string name
stock_entry = frappe.get_doc("Stock Entry", "SE-001")
stock_entry.customer = "CUST-001"  // References Selling module without importing it

// SchoolPilot3 (TypeScript): Module A gets typed access to Module B's data
const { stockEntries, customers } = useAppData()
// Stock module never imports Selling module, yet gets full type safety
// The types are "registered" via declaration merging at compile time
```

### Step 4: Understanding Barrel Imports vs Circular Dependencies

#### The Core Question

> "Wouldn't it be acceptable if every module exports what it has, and everything simply imports from core types?"

**Answer: Yes, in principle — but only if the barrel doesn't import back from modules.**

The problem is not the barrel pattern itself. The problem is that our current barrel (`@/core/types`) **imports from modules** via `app-data.ts`, creating a dependency graph where:
1. Modules import types from `@/core/types` (the barrel)
2. The barrel imports types from modules (via `app-data.ts`)
3. This creates a **two-way dependency** that is fragile and confusing

#### Concrete Example: The Nutrition -> Library Type Chain

```
nutrition/data/types.ts imports MealPlan from @/core/types
  -> @/core/types resolves to core/types/index.ts (barrel)
    -> core/types/index.ts exports from app-data.ts
      -> app-data.ts imports MealPlan from ../../modules/library/data/types
        -> library/data/types.ts exports MealPlan
```

This works today because `library/data/types.ts` does NOT import from `@/core/types`. But the chain is **indirect and fragile** — nutrition depends on library through a central hub it doesn't control.

#### The Broken Import: HR -> Finance

A more severe example:
```
hr/data/types.ts imports PayrollPeriod from @/core/types
  -> core/types/app-data.ts imports PayrollPeriod from ../../modules/finance/data/types
    -> BUT finance/data/types.ts does NOT export PayrollPeriod!
```

This is a **broken import chain** that likely resolves to `any` or fails silently. The types `PayrollPeriod`, `PayrollItemType`, `Payslip` are imported by `app-data.ts` from `finance/data/types.ts`, but they don't exist there. They're likely meant to come from HR's own data hooks.

#### Why Direct Imports Are Safer

```typescript
// BEFORE (fragile, 4-hop resolution):
import { MealPlan } from '@/core/types';
// nutrition -> barrel -> app-data -> library -> actual type

// AFTER (direct, 1-hop resolution):
import type { MealPlan } from '@/modules/library/data/types';
// nutrition -> library -> actual type
```

#### The Circular Dependency Risk With Module Augmentation

If we add `declare module '@/core/types'` in each module, AND those modules import from `@/core/types`, we create:

```
nutrition/appDataAugmentation.ts augments @/core/types
  -> nutrition/appDataAugmentation.ts imports MealPlan from @/core/types
    -> @/core/types (barrel) includes the augmentation
      -> circular reference: the augmentation augments a module it imports from
```

**This is NOT a runtime circular dependency** (TypeScript handles augmentation at compile time), but it IS a **circular type resolution** that can cause:
- TypeScript failing to resolve augmented types
- Ambiguous type errors
- Silent `any` typing

#### The Frappe/ERPNext Model

Frappe uses a **metadata registry** approach:
- DocTypes are defined as JSON schema files, not TypeScript interfaces
- A central registry loads all DocType definitions at runtime
- Cross-module references use string names (`"Student"`, `"Invoice"`), not type imports
- No compile-time type coupling between modules

Our project uses TypeScript, so we can't fully adopt the Frappe model. But we can learn from it: **modules should reference each other directly, not through a central hub that also imports from them.**

#### Recommended Import Strategy

| Scenario | Import From |
|----------|-------------|
| Module importing its OWN types | `./types` (relative) |
| Module importing another module's types | `@/modules/other/data/types` (direct) |
| Module importing truly universal types (enums, common) | `@/core/types` (barrel is safe for core-only) |
| Augmentation file referencing types | Same module's `./types` or direct `@/modules/other/data/types` |

**The barrel (`@/core/types`) should ONLY re-export types that are defined IN the core** — not types imported from modules. After this refactor, `@/core/types` should export: `common.ts`, `enums.ts`, `module.ts`, `moduleCollections.ts`, `moduleDataApi.ts`, and the base `app-data.ts` interfaces. It should NOT transitively re-export module-specific entity types.

- `PayrollPeriod`, `PayrollItemType`, `Payslip`, `StaffRecurringItem`, `StaffSalarySetting`, `PayslipItem`, `HRPayrollPeriodType` are NOT exported from any module's types file. - `app-data.ts` lines 47-50 incorrectly imports `PayrollPeriod`, `PayrollItemType`, `StaffSalarySetting`, `Payslip` from `finance/data/types.ts` — these imports should be removed or corrected

**Library module** (`src/modules/library/data/types.ts` lines 89-161): Defines `MealPlan`, `Menu`, `Merchant`, `StudentMealPlan`, `MealConsumptionLog`, `WalletTransaction`, `StudentWallet` — these are nutrition/wallet types that belong in the nutrition module, not library. This is the "meal plans in library not nutrition" issue.

**Decision:** For the scope of this refactor, we will NOT move types between modules (that would be a larger reorganization). Instead, we will:
1. Import types from wherever they are currently defined (even if misplaced)
2. Document the misplaced types as a separate cleanup issue
3. Ensure all imports use direct paths, not the barrel

## Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| Augmentation files not picked up by TypeScript | `tsconfig.json` already includes `src/**/*`, so all `.ts` files are compiled. No explicit import needed. |
| Circular dependencies between augmentation files | Use direct file imports (`@/modules/X/data/types`) instead of barrel imports (`@/core/types`) |
| Duplicate property names across modules | Follow existing naming convention (module-prefixed or domain-specific names like `studentInvoices`) |
| Runtime `APP_DATA_ARRAY_KEYS` mismatches compile-time `AppDataType` keys | Document that both `collectionConfig.ts` and `appDataAugmentation.ts` must be updated together |
| Breaking existing `any[]` consumers | Proper typing is the intended improvement; fix any type errors that surface |

## Critical Limitation: The Compilation Boundary Problem

TypeScript declaration merging has one catch: **augmented types are only known if the augmentation file is included in the compilation**. This is the compile-time equivalent of Frappe's runtime registry — if a module isn't "registered," its types don't exist.

In our monorepo setup, this is not a problem because:
- `tsconfig.json` includes all files under `src/**/*`
- All modules are compiled together in a single build graph
- No module is compiled in isolation without the others

However, if the project ever moves to a setup where modules are built independently (e.g., separate packages, micro-frontends), this approach would break. In that scenario, alternatives would be:

| Alternative | How It Works | Trade-off |
|-------------|--------------|-----------|
| Code Generation | Backend serves JSON Schema; frontend generates `types.ts` before build | Requires build step; true runtime schema evolution |
| Branded Strings + Type Guards | `getDoc(doctype: string)` returns `unknown`; caller uses type guards | Loses IntelliSense; runtime-safe but developer-unfriendly |
| Global `@types/` Package | All module augmentations published to a shared types package | Types can drift from runtime; extra maintenance |

For SchoolPilot3's current architecture (single Vite build, all modules in one repo), declaration merging is the optimal solution.

## Rollback Strategy

If issues arise, revert `src/core/types/app-data.ts` to its original state and delete the `appDataAugmentation.ts` files. The change is purely type-level with no runtime impact.
