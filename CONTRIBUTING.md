# Contributing to SchoolPilot3

Thanks for contributing! This guide covers the workflow and the conventions
that keep the codebase consistent. For architecture background see
[ARCHITECTURE.md](./ARCHITECTURE.md); for UI conventions see
[docs/contributing](docs/contributing). Taking part means agreeing to the
[Code of Conduct](./CODE_OF_CONDUCT.md); report a vulnerability privately per
[SECURITY.md](./SECURITY.md), never in a public issue.

## Getting started

### Prerequisites

- **Node 22** — the version CI pins in [`.github/workflows/ci.yml`](.github/workflows/ci.yml).
  There is no `.nvmrc` and no `engines` field in `package.json` yet, so that pin
  is the only source of truth: `TODO: owner to confirm the supported Node range and pin it.`
- **pnpm 10** — the version CI installs. `npm` and `yarn` are not supported.
- Git, with the repository hooks installed (`pnpm install-hooks`).

```bash
pnpm install --frozen-lockfile   # exact versions from pnpm-lock.yaml
pnpm dev                         # start the dev server
pnpm test:run                    # run the test suite once
pnpm typecheck                   # TypeScript project check (tsconfig.typecheck.json)
pnpm build                       # production build (vite + PWA)
```

Dependencies move only on purpose: a change to `package.json` needs a reason in
the pull request and the `pnpm-lock.yaml` regenerated by pnpm, never hand-edited.

## Test first

Every behaviour change starts with a failing test:

1. Write the test that describes the behaviour you want.
2. Run it and watch it fail for the right reason — a missing implementation, not
   a mistake in the test.
3. Write the smallest implementation that makes it pass.
4. Refactor with the test green.

Keep the tests you wrote. A source change without a test needs its reason stated
in the pull request, and "it should work" is not verification. Fix the cause of a
failure: never delete, skip or loosen a test to get a green run.

## The gate

Every change must pass the **gate** before it lands:

1. `pnpm typecheck` — error count must not increase. The ratchet is enforced:
   ```bash
   pnpm check:ratchet   # fails if the error count grew vs .type-ratchet
   ```
   If you genuinely fixed errors, lower the ratchet with
   `node scripts/check-type-ratchet.cjs --update`.
2. Targeted tests for the code you touched (`pnpm vitest run <paths>`).
3. `pnpm build` for structural changes (new files, imports, dependencies).
4. Commit with a conventional, specific message.

Small, logical commits beat large mixed ones.

### The PRD task gate

Work that belongs to a task in `docs/prd/` runs the same gate the task runs:

```bash
node scripts/prd/gate.mjs task --base <ref> --task <task-id>
```

`--base` is the ref the change is measured against (the branch you cut from, for
example `origin/consolidation`) and `--task` names the ledger task. A task gate
takes 8–12 minutes — typecheck, contract scan, related tests, lint — and writes
`.prd-gate/report.md`. It must end with `GATE PASSED`; any `FAIL` is blocking and
a `WARN` has to be explained in the pull request.

### Before you push

```bash
pnpm test:run                                  # the whole unit suite
pnpm lint                                      # ESLint over the repository
pnpm typecheck                                 # tsc -p tsconfig.typecheck.json
pnpm check:ratchet                             # the error count must not grow
pnpm secret:scan                               # no committed credentials
node scripts/audit/contract-scan.cjs --json    # every contract section empty
```

The golden paths run in a real browser: `pnpm test:e2e:gp1`.

## Code conventions

- **Tables**: use `DataGrid` (`@/components/ui/data`). See
  [docs/contributing/grids.md](docs/contributing/grids.md).
- **Forms**: use `EntityForm` for create/edit dialogs and `useValidation` for
  schema checks. See [docs/contributing/forms.md](docs/contributing/forms.md).
- **List pages**: follow the canonical CRUD pattern
  ([docs/contributing/crud.md](docs/contributing/crud.md)) with `useEntityCrud`.
- **Feedback**: `useToast()` for operation results; never `alert()`.
  Confirmations go through `useConfirm()`; never `window.confirm`.
- **Formatting**: `formatKES` / `formatDate` from `@/utils/format`.
- **Icons**: heroicons (`@heroicons/react/24/outline`) or `@/components/ui/icons`.
  Do not reintroduce lucide-react.
- No `window.confirm`, no `alert`, no new `as any` on touched lines.

## Data layer rules

- AppDataContext and the database services are **additive only**: new fields and
  functions may be added, existing contracts must not change.
- Route definitions, module registry, and provider selection are frozen unless
  a change is explicitly part of an agreed plan.
- New CRUD pages own their data via `useEntityCrud`; context reads are fine for
  reference data (departments, academic years, …).

## Tests

- Place tests next to the code or under `src/tests/`.
- Component tests must not depend on the global app providers — hooks like
  `useConfirm` fall back gracefully outside the app tree.
- Business-flow specs live in `src/tests/integration/`.

## Translations

The pre-commit hook runs a translation completeness check across all locales
(`en`, `fr`, `rw`, `sw`). If you add keys to an English namespace file, add the
same keys everywhere or the commit will be rejected.

## Pull request checklist

Copy this into the pull request description and tick every line.

- [ ] The gate passed and its table from `.prd-gate/report.md` is pasted in,
      ending `GATE PASSED` (with any `WARN` explained).
- [ ] Tests cover the change and fail without it; that failing run was seen.
- [ ] `pnpm test:run` passed locally, or the remaining failures are named and
      pre-existing.
- [ ] No `--no-verify`, no skipped or deleted test, no raised `.type-ratchet`,
      no edits to `docs/prd/gate-baseline.json`.
- [ ] Docs updated: behaviour, pack data or an RFC, whichever the change touches.
- [ ] No secrets, tokens, DSNs or personal data in the diff or the description.
- [ ] Any contributed data has a licence and a source; a pack change cites the
      official document and its URL.
- [ ] The diff stays inside the files the task owns.

## PRD tasks: ledger discipline

Tasks under `docs/prd/` follow [EXECUTION.md](docs/prd/EXECUTION.md): one task,
one commit, one gate run on the task branch.

- Edit only the files the task lists. Needing another task's file means the task
  is blocked, not that the file is yours.
- Do not edit `docs/prd/tasks.json`, `docs/prd/LOCAL-HANDOFF.md`,
  `docs/prd/SCORECARD*.md`, `docs/prd/gate-baseline.json` or
  `docs/prd/workflow-log/*`: the integrator records results at integration.
- New translation keys go to `docs/prd/workflow-log/pending-i18n/<task-id>.json`
  and are merged by the wave's integration task, so parallel tasks never collide
  in a shared locale file.

## Correcting a pack

Packs are data, and a correction is accepted only with evidence.

1. Open a **Pack correction** issue
   ([`.github/ISSUE_TEMPLATE/pack_correction.md`](.github/ISSUE_TEMPLATE/pack_correction.md))
   with the pack id and version, the URL of the official source document, the
   current behaviour, the expected behaviour, and a conformance vector or example.
2. A pack steward checks the source and the version bump: **patch** for a label
   or comment fix, **minor** for a new option or template, **major** for a
   structural change to levels or learning areas (spec 03 §2.3).
3. `verified` status is granted only when the pack's conformance vectors are
   traced to an official worked example. Roles and the steward list live in
   [docs/packs/STEWARDSHIP.md](docs/packs/STEWARDSHIP.md).

A programme that has no pack at all goes through
[`.github/ISSUE_TEMPLATE/pack_request.md`](.github/ISSUE_TEMPLATE/pack_request.md)
first.

## Branches, commits and pull requests

Branch names say what the change is: `prd/<task-id>` for a PRD task (for example
`prd/P0-C03`), `fix/<slug>` for a bug, `docs/<slug>` for documentation, and
`prd/<task-id>-fix<n>` for a fix round after review. Nothing is committed
straight to `consolidation` or `main`.

Commit subjects follow [EXECUTION.md §3](docs/prd/EXECUTION.md):

```
<type>(<scope>): <imperative summary> [<task-id>]

<what changed and why, 2–6 lines>

Requirements: FR-01
Gate: task PASS — tsc 3041/3056, missingNames 120/138, contracts ↓ undefinedCollections 8/10, related tests 14 passed
```

`type` is one of `fix`, `feat`, `refactor`, `test`, `chore`, `docs`, `perf`,
`build`, `ci`. One logical change per commit; the subject is imperative and the
body says why, not what.

Open the pull request against `consolidation`, describe it with
[`.github/pull_request_template.md`](.github/pull_request_template.md), and keep
it to one task or one coherent change.
