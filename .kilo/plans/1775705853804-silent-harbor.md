# Modularity Architecture Cleanup Plan (Final)

## Executive Summary

**Goal:** True modularity where modules are self-contained, core is infrastructure-only, and the existing modular infrastructure is fully utilized.

**Key Principles:**
1. Core does not know modules exist (no imports from modules)
2. Modules export what they want to share
3. Cross-module dependencies are explicit in module.json
4. Contexts are conditional based on module state
5. Shared data access via `useSharedData()` hooks
6. Cross-module services via `ServiceRegistry`

## Problem Analysis (Detailed)

### Current Violations with File Evidence

| Issue | File Path | Problem |
|-------|-----------|---------|
| Core knows about modules | `src/core/types/finance.ts` | Contains FeeTemplate, Invoice, Payment types |
| Core knows about modules | `src/core/types/hr.ts` | Contains PayrollPeriod, Payslip types |
| Core knows about modules | `src/core/types/inventory.ts` | Contains StockLevel, Requisition types |
| Core owns module code | `src/contexts/data/FinanceDataContext.tsx` | Module context in core |
| Core owns module code | `src/contexts/data/HRDataContext.tsx` | Module context in core |
| Core owns module code | `src/hooks/data/useFinanceData.ts` | Module hook in core |
| Core owns module code | `src/hooks/data/useHRData.ts` | Module hook in core |
| Type duplication | `src/core/types/finance.ts` vs `src/modules/finance/data/types.ts` | Same types in two places |
| Circular dependency | `src/core/types/app-data.ts` imports from modules | Creates import cycle |
| Global re-export | `src/types.ts` exports module types | Modules should export themselves |

### Current Architecture Problems

1. **Module-Specific Code in Core Folders**
   - `src/contexts/data/` contains 8 module-specific contexts
   - `src/hooks/data/` contains 11 module-specific hooks
   - These should be inside each module's folder

2. **Type Ownership Confusion**
   - `src/core/types/` contains domain-specific types
   - Each module also defines its own types in `src/modules/X/data/types.ts`
   - No clear single source of truth

3. **Underutilized Modular System**
   - `ModuleRegistry`, `ServiceRegistry`, `ModuleExports`, `ModuleLoader` are fully implemented
   - But modules are statically registered in `moduleRegistration.ts`
   - Dynamic loading infrastructure is present but unused

4. **Context-System Disconnect**
   - `moduleRegistry.isEnabled()` exists but data contexts ignore it
   - All 8 data contexts are always rendered regardless of module state

5. **Database Access Patterns**
   - Each module context queries data independently
   - No unified shared data access pattern

## Phase 3: Conditional Context System (Week 3)

**Objective:** AppDataContext conditionally renders providers based on module state.

### 3.1 Problem

Current AppDataContext.tsx wraps ALL 8 providers unconditionally:

```tsx
return (
  <SystemDataProvider>
    <AdministrationDataProvider>
      <FinanceDataProvider>
        <HRDataProvider>
          {/* ... all 8 always rendered */}
        </HRDataProvider>
      </FinanceDataProvider>
    </AdministrationDataProvider>
  </SystemDataProvider>
);
```

### 3.2 Solution

```tsx
// AppDataContext.tsx - conditional rendering
return (
  <CoreDataProvider>
    {moduleRegistry.isEnabled('system') && (
      <SystemDataProvider>{children}</SystemDataProvider>
    )}
    {moduleRegistry.isEnabled('administration') && (
      <AdministrationDataProvider>{children}</AdministrationDataProvider>
    )}
    {moduleRegistry.isEnabled('finance') && (
      <FinanceDataProvider>{children}</FinanceDataProvider>
    )}
    {moduleRegistry.isEnabled('hr') && (
      <HRDataProvider>{children}</HRDataProvider>
    )}
    {/* ... etc for all modules */}
  </CoreDataProvider>
);
```

### 3.3 Safe Context Hooks

Create wrapper hooks that check module state:

```typescript
// modules/finance/data/useSafeFinanceContext.ts
export const useSafeFinanceContext = () => {
  const isEnabled = moduleRegistry.isEnabled('finance');
 
  if (!isEnabled) {
    return {
      chartOfAccounts: [],
      banks: [],
      suppliers: [],
      // ... empty/no-op data
      isModuleEnabled: false,
    };
  }

  return { ...useFinanceDataContext(), isModuleEnabled: true };
};
```

## Phase 5: Service Registry Integration (Week 5)

**Objective:** Cross-module business logic via ServiceRegistry.

### 5.1 Module Service Registration

```typescript
// modules/finance/services/InvoiceService.ts
export class InvoiceService {
  async generateInvoice(studentId: string): Promise<Invoice> { ... }
  async processPayment(invoiceId: string, amount: number): Promise<void> { ... }
}

// Register in module lifecycle
serviceRegistry.register({
  name: 'InvoiceService',
  moduleId: 'finance',
  factory: () => new InvoiceService(),
  singleton: true
});
```

### 5.2 Cross-Module Service Access

```typescript
// Portal module accessing Finance service
const invoiceService = await serviceRegistry.get<InvoiceService>('finance', 'InvoiceService');
const invoice = await invoiceService.generateInvoice(studentId);
```

### 5.3 Service-Facing Hook

```typescript
// src/hooks/useService.ts
export const useService = <T>(moduleId: string, serviceName: string): T | null => {
  const [service, setService] = useState<T | null>(null);
 
  useEffect(() => {
    serviceRegistry.get<T>(moduleId, serviceName).then(setService);
  }, [moduleId, serviceName]);
 
  return service;
};

// Usage
const invoiceService = useService<InvoiceService>('finance', 'InvoiceService');
```

## Phase 8: Lint Script Enhancement (Week 7-8)

**Objective:** Comprehensive architectural enforcement.

### 8.1 Blocked Patterns

```typescript
// detect-cross-module-imports.ts

// 1. Core importing from modules
if (file.includes('/core/') && line.match(/from\s+['"]@\/modules\/([^'"]+)/)) {
  violations.push({ type: 'core-imports-module', severity: 'error' });
}

// 2. Importing from old context locations
if (line.match(/from\s+['"]@\/contexts\/data\/([^'"]+)/)) {
  violations.push({ type: 'old-context-import', severity: 'error' });
}

// 3. Importing from old hook locations
if (line.match(/from\s+['"]@\/hooks\/data\/([^'"]+)/)) {
  violations.push({ type: 'old-hook-import', severity: 'error' });
}

// 4. Implicit module dependencies
if (file.includes('/modules/') && line.match(/from\s+['"]@\/modules\/([^/]+)/)) {
  const fromModule = extractModuleFromPath(file);
  const toModule = extractModuleFromImport(line);
  if (fromModule !== toModule && !hasDependencyDeclared(fromModule, toModule)) {
    violations.push({ type: 'implicit-dependency', severity: 'error' });
  }
}
```

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Breaking existing functionality | Medium | High | Extensive testing after each phase, phased rollout |
| Type import cascade failures | High | High | Use TypeScript strict mode, fix imports in same PR |
| Circular dependencies | High | High | Careful refactoring, use detection tools |
| Performance issues with dynamic loading | Low | Medium | Optimize lazy loading, add caching |
| Developer confusion during transition | Medium | Low | Comprehensive documentation, clear migration guide |
| Context-provider order breaking | Medium | Medium | Verify provider hierarchy after moving contexts |

### Risk Mitigation Strategies

1. **Before migration:** Add eslint rules to flag old imports
2. **During migration:** Update imports in same PR as file move
3. **After migration:** Old import paths simply don't exist (clear error)
4. **Test after each phase:** Run `npm run lint:modules` and tests
5. **Document changes:** Keep detailed notes of what was changed and why

## Clarifications

### Q: Should AppDataContext conditional rendering be done per-module or all at once?
**A:** Per-module during pilot. Start with Finance in Phase 2. Once Finance works with conditional rendering, replicate pattern for other modules in Phase 3.

### Q: What about database schemas - does core import them?
**A:** Core should NOT import module schemas. UnifiedDatabaseManager discovers schemas at runtime through module registration. Verify no core files import from `@/modules/X/data/schema`.

### Q: Types vs Services for cross-module communication?
**A:** 
- **Types:** Import types directly with explicit dependency in module.json
- **Runtime data:** Use `useSharedData()` hooks
- **Business logic:** Use `ServiceRegistry`
